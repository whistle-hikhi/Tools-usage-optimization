# LLM Agent Tool Use: Failure Modes, Mitigations, and Open Research Gaps

## What are the documented failure modes in LLM tool use?

### Takeaway
The literature converges on a recurring set of failure modes — tool/argument hallucination, unnecessary or redundant tool calls, wrong tool selection among similar candidates, context-window/accuracy collapse as tool-set size grows, result-ignoring, and brittle error recovery — and several 2025-2026 papers now propose formal taxonomies and benchmarks specifically to diagnose these, rather than only measuring end-to-end task success.

### Cited Findings
- **ToolFailBench taxonomy (2026)** formalizes four failure categories for tool-required tasks plus two for "control" (no-tool-needed) tasks: (1) **Tool-Skip (TS)** — "Model did NOT make a valid, executed tool call," including no call, unexecuted text-formatted calls, or refusal; (2) **Result-Ignore (RI)** — "Model called the correct tool, received the return value, but the final answer does NOT faithfully reflect it," evidenced by memorized values replacing tool data, empty answers despite data received, or contradictions; (3) **Output-Fabrication (OF)** — "Answer contains invented structured data (fake JSON, hallucinated table rows, fabricated numbers, named entities not in tool return)," distinguished from Result-Ignore by looking plausible; (4) **Unnecessary-Tool-Use (UTU)** — "Model called a tool when none was needed" — [ToolFailBench: Diagnosing Tool-Use Failures in LLM Agents](https://arxiv.org/html/2607.04686)
- Quantitatively, even the best model tested (Grok-4.3) reached only an **86.33% Clean Tool-Use Rate**, showing tool use is far from saturated; some Llama-3.1 models exhibit an "Always-Call" pattern with Unnecessary-Tool-Use Rate ≥77%; Llama-3.1-70B and Qwen2.5-72B differ by 89 percentage points on control-task accuracy; the Finance domain shows the highest median Result-Ignore Rate (12.24%) vs. Cybersecurity (0.68%) — [ToolFailBench](https://arxiv.org/html/2607.04686)
- The **Berkeley Function-Calling Leaderboard (BFCL)** AST checker "categorizes responses into seven outcome categories spanning error severity: syntax errors, type errors, hallucinated tool or parameter names, unnecessary tool-calls, and missing parameters" — [Why Does Function Calling Lower Model Accuracy on Berkeley Leaderboard?](https://github.com/ShishirPatil/gorilla/discussions/606)
- A quality audit of BFCL itself found **defects in 48% of 50 randomly sampled questions**, with category-specific defect rates from 20% (non-live AST) to 70% (memory); a defect is defined as a case "where a fully correct, instruction-following response could be marked wrong (false negative), or where a clearly incorrect response could be marked correct (false positive)" — e.g., a watchlist-add task where the correct behavior (checking first, making no call) causes the model to "fail the turn entirely" under the benchmark's scoring — [BFCL v4 review, Epoch AI](https://epoch.ai/benchmarks/berkeley-function-calling-leaderboard/review)
- On the gap between function-calling (FC) mode and prompt-based tool use: GPT-4-1106-Preview scored **85.65% accuracy via prompting vs. 79.65% via native FC**, attributed by the benchmark maintainers to FC implementations having "very limited capability" — e.g., some models don't support multiple or parallel function calls — meaning the dedicated tool-calling interface itself can be a source of failure relative to prompting — [BFCL discussion #606](https://github.com/ShishirPatil/gorilla/discussions/606)
- **Tool hallucination** is defined as occurring "when an LLM agent invokes tools that do not exist or are inappropriate for the task," with two sub-types: non-existent tools (not in the toolkit) and inappropriate tool selection (valid tool, wrong fit) — [Closed-World Resolution Against Tool Hallucination in LLM Agents](https://arxiv.org/pdf/2609.19425)
- A finer split distinguishes **Tool Selection Hallucinations (TSHs)** — "non-existent or irrelevant tools being chosen overconfidently" — from **Tool Calling Hallucinations (TCHs)** — "incorrect, omitted, or fabricated parameter fillings" — [search synthesis, "hallucinated tool calls LLM agents"]; illustratively, "a model that has seen `delete_file` in a thousand traces will happily emit `wipe_disk`; a model that knows `transfer_funds` takes an amount will invent an override flag the schema never declared" — framed as a structural gating gap: "a gate can only decide about a tool it placed in the visible set; a hallucinated tool is by definition not something a gate chose to expose" — [search synthesis citing tool-hallucination literature]
- **Context/scale degradation**: on BFCL, accuracy for a calendar-scheduling task **dropped from 43% to 2%** when the tool set expanded from 4 to 51 tools; 58 tool definitions consume "roughly 55,000 tokens," imposing baseline overhead "equivalent to summarizing a short novel before the user's query even enters"; tools placed in the **middle of a list** show only 22-52% accuracy vs. 31-32% for tools at the beginning/end (a "lost in the middle" effect for tool lists) — [The Over-Tooled Agent Problem, TianPan.co](https://tianpan.co/blog/2026-04-19-over-tooled-agent-problem)
- With a large tool set, baseline tool-selection accuracy can be **as low as 13.62%**; retrieval-augmented filtering (Tool RAG) raised this to 43% — a 3x improvement — [search synthesis / Tool Selection Problem, TianPan.co](https://tianpan.co/blog/2026/04/09/tool-selection-problem-agent-tool-routing-at-scale)
- RAG-MCP's own framing: "flooding a model's context window with too much information can actually degrade reasoning. Functions start to blur together, and even advanced models struggle to pick the right one," identifying three hurdles — managing hundreds of tools without manual descriptions, ensuring correct tool selection, and preventing context-window bloat — [When too many tools become too much context, Writer Engineering](https://writer.com/engineering/rag-mcp/)
- Separately, Llama 3.1 8B "failed despite having ample context window" with 46 tools but succeeded with 19; OpenAI's o3 accuracy fell from 98.1% to 64.1% as tool count grew; long-context models show accuracy drops of 7–85% as tool count increases; once tool count exceeds roughly 30, "tool descriptions begin overlapping and the model struggles to choose correctly" — [LogRocket / search synthesis on context-window tool degradation]
- A **chance-corrected analysis** ("How Many Tools Should an LLM Agent See?") finds fixed tool-list sizes harm performance in both directions: "Show too many tools and the model struggles to choose. Show too few and the correct tool may not appear." On BFCL (370 tools), an adaptive approach reached "90.3±2.4% coverage at K=7.4," matching performance of showing 50 tools (a 7× reduction in candidates shown). On ToolBench (3,251 tools), a fixed K=5 had higher aggregate coverage (64.7% vs. 61.9%) but "finds nothing on hard queries (correct tool ranked 6th–20th)," while the adaptive agent found 16.7% of those hard cases. Downstream choice accuracy with adaptive (shorter) lists was 93.1% vs. 87.1% for fixed K=5, widening to 76.8% vs. 60.9% on medium-difficulty queries — [How Many Tools Should an LLM Agent See? A Chance-Corrected Answer](https://arxiv.org/html/2605.24660v1)
- Production-level taxonomy: LLM agents in deployment "fail in five recurring operational families: wrong task outcomes, bad tool actions, lost or corrupted state, policy or security violations, and loops or waste" — the "loops or waste" family directly corresponds to redundant/duplicate tool calls and runaway retries — [5 Failure Modes of Production LLM Agents, Latitude.so](https://latitude.so/blog/the-5-failure-modes-every-production-llm-agent-has)
- On safety-adjacent failure: "Models tend to ignore necessary tools when multiple tools are given in one task, and often fabricate parameters to call tools when insufficient information is provided" — [Agent-SafetyBench search synthesis](https://arxiv.org/pdf/2412.14470)
- "Constraint Tax" phenomenon: structured-output constraints (used to prevent malformed arguments) can themselves **suppress tool calling** in open-weight models — a direct tension between the fix for one failure mode (malformed args) and causing another (tool-skip) — [Constraint Tax in Open-Weight LLMs](https://arxiv.org/html/2606.25605v1)
- Cascading/compounding errors and stability under adversarial or shifted conditions are studied in "More Vulnerable than You Think: On the Stability of Tool-Integrated LLM Agents," indicating that a single erroneous intermediate tool call/result can propagate through multi-step agent trajectories — [arXiv 2506.21967](https://arxiv.org/pdf/2506.21967)
- The **Tool Learning with Large Language Models survey** (Qu, Dai, Wei, Cai, Wang, Yin, Xu, Wen; submitted 28 May 2024, revised 4 Nov 2024) frames the whole pipeline — task planning → tool selection → tool calling → response generation — as the structure within which these failures occur, and explicitly notes "the existing literature remains fragmented and lacks systematic organization," implying failure modes have historically been studied piecemeal rather than end-to-end — [Tool Learning with Large Language Models: A Survey, arXiv:2405.17935](https://arxiv.org/abs/2405.17935)

### Inferences
- Failure modes cluster into three stages matching the survey's own taxonomy: *selection-stage* failures (wrong tool among similar candidates, tool hallucination, context-bloat-induced misselection), *calling-stage* failures (argument/parameter hallucination, malformed arguments), and *post-call* failures (Result-Ignore, Output-Fabrication, failure to recover from execution errors).
- "Unnecessary tool use" and "tool skip" sit at opposite ends of a single miscalibration axis — models seem to adopt either an "always-call" or "under-call" policy rather than a calibrated, query-conditional one, which is exactly the accuracy-vs-efficiency calibration problem a workshop paper on "choosing the optimal way to handle tasks" could target.
- The accuracy collapse as tool count grows (43%→2% on an 11x tool-count increase; 90%→2-52% in positional effects) is probably the single most quantitatively dramatic and benchmarkable failure mode for a workshop paper, since it directly operationalizes an efficiency/context-cost vs. accuracy tradeoff.

## What mitigation techniques have been proposed for each failure mode?

### Takeaway
Mitigations map fairly cleanly onto failure stages: retrieval-based tool filtering and adaptive-K selection address context-bloat/wrong-selection; constrained decoding and schema-aware generation address argument hallucination/malformed calls; closed-world resolution and probe-based detection address hallucinated tool names; and structured self-correction/checklists plus differentiated recovery policies address execution-error recovery and result-ignoring — though several of these mitigations carry their own tradeoffs (e.g., constrained decoding can suppress tool-calling itself).

### Cited Findings
- **Retrieval-augmented tool selection (Tool RAG / RAG-MCP)**: embed query and tool descriptions in a shared vector space, rank by similarity, inject only the top-relevant subset into context ("embed and search," "rank and select," "inject and reason"), separating "what to remember" from "how to think." Reported to "more than triple tool-selection accuracy" (13%→43%) "and reduce prompt tokens by over 50%" — [RAG-MCP, Writer Engineering](https://writer.com/engineering/rag-mcp/); corroborated by the Tool RAG accuracy improvement figure elsewhere ("13% to 43%, a 3x improvement") — [search synthesis, TianPan.co]
- **Adaptive/chance-corrected tool-set sizing**: rather than a fixed top-K, select K per-query using a chance-corrected "Bits-over-Random" (BoR = log₂(P_obs/P_rand)) selectivity metric so "the reward naturally decreases with depth, reducing the need for an engineered depth penalty." On BFCL this matched fixed-K=50 performance using K≈7.4 (7x fewer candidates); on hard ToolBench queries it recovered answers (16.7%) that fixed K=5 missed entirely — [How Many Tools Should an LLM Agent See?](https://arxiv.org/html/2605.24660v1)
- **Probe&Prefill** approach: adjusting a probe's decision threshold "provides smooth, fine-grained control over the accuracy–efficiency tradeoff," reported to reduce tool calls by 48% with only 1.7% accuracy loss — [search synthesis citing Probe&Prefill, from "tool selection accuracy efficiency tradeoff" search]
- **Hierarchical approaches / lazy-loading routing**: beyond "roughly 10-20 tools per context, adding capability destroys the ability to use it"; the proposed fix is systems where "routing, hierarchy, and lazy-loading ensure each agent call sees only the tools it needs" — [search synthesis, TianPan.co "over-tooled agent" post]
- **Constrained decoding / grammar-based structured generation** for tool arguments: "modifies an LLM's next-token predictions based on predefined constraints to prevent the generation of tokens that would lead to undesirable output sequences," with the grammar engine masking logits for illegal tokens at each step. Applied to tool calls, this "eliminates malformed tool call arguments as a failure category" since "argument hallucination (a string where an integer belongs, an unknown enum) is exactly what constrained decoding eliminates." Tools: OUTLINES (FSM-based vocabulary indexing), xgrammar, OpenAI structured outputs (compiles JSON Schema to guarantee validity), Anthropic "strict tool use" (guarantees arguments match schema). After a one-time grammar-compilation cost (cached), "constrained latency is comparable to unconstrained" — [Structured Output for LLMs: Constrained Decoding, search synthesis](https://www.gmicloud.ai/en/blog/structured-output-for-llm-inference-json-schema-enforcement-constrained-decoding-and-parse-failure-rates)
- **Tradeoff/limitation of constrained decoding**: the "Constraint Tax" finding shows structured-output constraints can *suppress tool calling itself* in open-weight models — i.e., a mitigation for one failure mode (malformed arguments) can induce another (tool-skip) — [Constraint Tax in Open-Weight LLMs](https://arxiv.org/html/2606.25605v1); related work on "retrieval-augmented generation and constrained decoding" jointly mitigates errors in LLM-generated Web API invocations — [Mitigating Errors in LLM-Generated Web API Invocations, arXiv:2607.05936](https://arxiv.org/pdf/2607.05936)
- **Closed-world resolution** against tool hallucination: constrains agent responses to only acknowledge explicitly-provided tools via prompt engineering and response filtering, "significantly reduces hallucination rates across multiple benchmark datasets," with reported effectiveness particularly for "well-defined, limited tool vocabularies" — but the authors flag that "how the approach performs with large, dynamically expanding tool sets remains unclear," that overly restricting agent creativity could cause "potential performance degradation," and that there is "limited evidence regarding transferability across different agent architectures" — [Closed-World Resolution Against Tool Hallucination in LLM Agents, arXiv:2609.19425](https://arxiv.org/pdf/2609.19425)
- **Probe-based detection of tool-calling errors from internal model states**: "A Few Neurons Reveal When LLMs Misuse Tools" proposes sparse detection and selective steering using internal neuron activations to catch misuse before/as it happens, rather than post-hoc output filtering — [arXiv:2608.00218](https://arxiv.org/pdf/2608.00218); similarly, "The Calls are Coming from Inside the Model" investigates probe-based detection of tool-calling errors directly from internal representations — [arXiv:2608.27750](https://arxiv.org/pdf/2608.27750); and tool-call dependency structure is shown to be "linearly decodable in LLM agent residual streams," suggesting internal-state probes as a lightweight verification layer — [arXiv:2605.25310](https://arxiv.org/pdf/2605.25310)
- **Hierarchical Error Checklists** for tool learning: guides a self-correction loop where the model uses a hierarchical checklist to diagnose the specific error category in a failed tool call, then regenerates/validates the correction against the diagnosed error before accepting it; reported to improve tool-learning performance across multiple benchmarks (exact deltas not confidently extractable from the fetched PDF) — [Enhancing Tool Learning in Large Language Models with Hierarchical Error Checklists, arXiv:2506.00042](https://arxiv.org/pdf/2506.00042)
- **Differentiated error-recovery policies** (vs. generic retry): systems define a recovery-action space — "Retry, Skip, Replan, Substitute_Tool, Escalate_Fidelity, Regenerate_Prior_Step, or Escalate" — and research shows "different failure classes benefit from different recovery actions, with retry being useful for transient failures but poorly matched to stale retrieval context, schema drift, contradictory evidence, or wrong-but-plausible semantic outputs," i.e., naive retry-on-failure is an inadequate universal mitigation — [search synthesis on "LLM agent self-correction retry tool execution error recovery"]
- **AgentDebugX**: an open-source toolkit organizing failure handling as a closed loop of "Detect, Attribute, Recover, and Rerun," for failure observability and attribution in LLM agents — [AgentDebugX, arXiv:2607.18754](https://arxiv.org/html/2607.18754)
- **Self-Healing Agentic Orchestrators**: enable automatic recovery by marking failed tool paths as high-cost and finding alternative execution paths — effectively a graph/routing-based fallback mechanism rather than blind retry — [Self-Healing Agentic Orchestrators, arXiv:2606.01416](https://arxiv.org/html/2606.01416v1); a related "Graph-Based Self-Healing Tool Routing for Cost-Efficient LLM Agents" explicitly frames recovery as a cost-efficiency problem — [arXiv:2603.01548](https://arxiv.org/pdf/2603.01548)
- **Structured reflection**: "Failure Makes the Agent Stronger: Enhancing Accuracy through Structured Reflection for Reliable Tool Interactions" proposes using structured reflection on failures (rather than unstructured retries) to improve reliability — [arXiv:2509.18847](https://arxiv.org/pdf/2509.18847)
- **Natural-language tool calling** (as an alternative to JSON-schema function calling) is proposed as a way to reduce schema-adherence failures by having the model describe the call in natural language rather than strict structured syntax — [Natural Language Tools, arXiv:2510.14453](https://arxiv.org/pdf/2510.14453)
- For edge/resource-constrained deployment, "Less is More: Optimizing Function Calling for LLM Execution on Edge Devices" treats minimizing exposed tool/function surface as itself the mitigation for both cost and accuracy issues — [arXiv:2411.15399](https://arxiv.org/pdf/2411.15399)
- CITI and similar fine-tuning approaches aim to "enhance tool utilizing ability... without sacrificing general performance," i.e., training-time mitigation rather than inference-time filtering/decoding — [CITI, arXiv:2409.13202](https://arxiv.org/pdf/2409.13202)

### Inferences
- Mitigation techniques form a layered stack: (1) *pre-selection filtering* (RAG-MCP, adaptive-K, hierarchical routing) to fix context-bloat/wrong-selection before generation; (2) *generation-time constraints* (constrained decoding, strict schemas, closed-world prompting) to fix malformed/hallucinated calls during generation; (3) *post-call diagnosis and recovery* (checklists, differentiated recovery policies, structured reflection, self-healing routing) to fix execution failures and result-ignoring after the call. A workshop paper proposing "optimal task handling without dropping accuracy" could position itself as unifying stage (1) and stage (3) — i.e., deciding *when* to pay the cost of more tools/more verification vs. when a cheaper path suffices — since stage (2) mitigations are comparatively mature (constrained decoding) while the selection/recovery-policy tradeoff is less settled.
- No mitigation found directly targets "confidence thresholds / calibration" for the decision of whether to call a tool at all (the Tool-Skip vs. Unnecessary-Tool-Use dilemma) as a first-class, named technique — the closest are Probe&Prefill's threshold-tunable accuracy/efficiency control and the internal-neuron-probe detection papers, which are closer to error *detection* than pre-call confidence calibration.

## What do recent survey papers explicitly list as open problems / future directions, especially on efficiency-accuracy tradeoffs?

### Takeaway
Multiple 2024-2026 surveys explicitly flag tool-orchestration/tool-selection robustness, standardized fine-grained (not just end-to-end) evaluation, and self-evolving/trust-utility tradeoffs as open; the clearest *efficiency-accuracy tradeoff* framing comes not from the canonical surveys (whose stated gaps were only partially extractable verbatim) but from recent empirical papers that explicitly name "no standard methodology exists to tell the builder whether the chosen K was appropriate" as an open problem.

### Cited Findings
- The **Tool Learning with Large Language Models survey** (arXiv:2405.17935, Qu et al., submitted 28 May 2024, revised 4 Nov 2024) states its aim "to inspire both researchers and industrial developers to further explore this emerging and promising area," and frames the field's literature as "fragmented and lacks systematic organization" — implying efficiency-accuracy tradeoffs in tool selection/invocation remain an unconsolidated research area rather than one with settled open-problem statements extractable from the abstract alone — [arXiv:2405.17935](https://arxiv.org/abs/2405.17935)
- A broad LLM-agent survey synthesis reports: "Major trends show that multimodal reasoning and tool orchestration remain unresolved challenges, with over 90% of systems lacking explicit trust and safety mechanisms" and that "open challenges include alignment stability, explainability, governance, and robust evaluation frameworks," plus "self-evolving agents, runtime monitoring and verification, privacy-preserving personalization, and the trust-utility trade-off" — [search synthesis of recent LLM-agent surveys, incl. "A Review of Prominent Paradigms for LLM-Based Agents," ACL Anthology COLING 2025](https://aclanthology.org/2025.coling-main.652.pdf)
- Explicitly on evaluation granularity: "Many current benchmarks rely on coarse-grained end-to-end success metrics that obscure insights into intermediate decision processes such as tool selection and reasoning quality, necessitating standardized, fine-grained evaluation metrics" — [search synthesis, citing "A Survey on Evaluation of LLM-based Agents," arXiv:2503.16416](https://arxiv.org/html/2503.16416v2)
- Future-direction statement from a tool-learning-focused synthesis: "Three key future directions for tool learning agents include VLM agents and tools, multi-agent frameworks for tools, and unified format toolsets," plus "developing universal tool-use workflows, as current research tends to focus on tools for specific tasks rather than universally applicable paradigms" — [search synthesis citing "LLM-Based Agents for Tool Learning: A Survey," Springer, 2025](https://link.springer.com/article/10.1007/s41019-025-00296-9)
- A dedicated efficiency-focused survey title directly names this gap: **"Toward Efficient Agents: Memory, Tool learning, and Planning"** (arXiv:2601.14192) — its existence as a standalone 2026 survey indicates the field has only recently begun treating "efficiency" (as distinct from raw accuracy) as a first-class survey axis for tool-using agents — [arXiv:2601.14192](https://arxiv.org/pdf/2601.14192)
- The clearest explicit open-problem statement found anywhere in this research, directly on the efficiency-accuracy tradeoff for tool selection: **"No standard methodology exists to tell the builder whether the chosen K was appropriate,"** and existing benchmarks "were not designed to evaluate search depth," explicitly calling for "a purpose-built benchmark with controlled difficulty distributions" — [How Many Tools Should an LLM Agent See? A Chance-Corrected Answer, arXiv:2605.24660](https://arxiv.org/html/2605.24660v1)
- ToolFailBench's stated future work: "release an evaluation harness for users to run models and receive failure-mode breakdowns, expand datasets across more domains and multi-turn variants, and test whether same failure modes persist in longer, realistic tool-use settings" — i.e., an explicit call to move from single-turn, isolated failure diagnosis toward multi-turn, realistic settings — [ToolFailBench, arXiv:2607.04686](https://arxiv.org/html/2607.04686)
- "A Taxonomy of Failures in Tool-Augmented LLMs" (Cailin Winston et al., ASE/testing venue) frames its contribution as enumerating "possible failures and their root causes based on literature survey and in-depth analysis of published tool-augmented LLMs," identifying "six main failure root causes and their affected system components" — a direct statement that, prior to this taxonomy, failure root-causes were not systematically mapped to system components — [A Taxonomy of Failures in Tool-Augmented LLMs](https://homes.cs.washington.edu/~rjust/publ/tallm_testing_ast_2025.pdf)
- "Failure Modes in LLM Systems: A System-Level Taxonomy for Reliable AI Applications" (arXiv:2511.19933) similarly argues for a system-level (rather than purely model-level) taxonomy, implying existing failure categorizations stop at the model/tool-call level and miss system-level compounding — [arXiv:2511.19933](https://arxiv.org/abs/2511.19933)

### Inferences
- The survey literature's open-problem statements are mostly *qualitative* ("robust evaluation," "trust-utility trade-off," "universal workflows") while the sharpest, most *quantitative and actionable* open-problem statement — "no standard methodology exists to tell the builder whether the chosen K was appropriate" — comes from a narrower, recent empirical paper rather than a broad survey. This is a strong candidate gap statement for motivating a workshop paper: the field lacks a principled, benchmarked way to decide the efficiency/accuracy operating point for tool exposure/invocation, as opposed to just building more retrieval heuristics.
- The repeated emergence of "efficiency" as a newly-separated survey axis (e.g., arXiv:2601.14192 titled "Toward Efficient Agents") in 2026, after several years of accuracy-only surveys, suggests the research community is only now formalizing efficiency-accuracy tradeoffs as a named subfield — good timing/framing support for a workshop paper on this exact topic.

## Are there position papers / critical analyses arguing current tool-use benchmarks/approaches are inadequate for measuring real-world efficiency-accuracy tradeoffs?

### Takeaway
Yes — several 2025-2026 papers explicitly argue current tool-use benchmarks are too narrow, too coarse-grained, or internally defective to measure real-world tool-selection/invocation tradeoffs, spanning benchmark-quality audits (BFCL), scope critiques (MCP-Bench, fragmented evaluation), and depth-of-search critiques (the chance-corrected tool-count paper).

### Cited Findings
- The **BFCL quality audit** found defects in 48% of sampled questions overall (20-70% by category), concluding that a benchmark widely used as the field's standard for function-calling accuracy itself contains enough false negatives/positives to distort measured accuracy — a direct critical claim that current benchmark scores may not reflect true tool-use competence — [BFCL v4 review, Epoch AI](https://epoch.ai/benchmarks/berkeley-function-calling-leaderboard/review)
- Synthesis of benchmark-critique papers: "Existing benchmarks for tool use remain fundamentally limited despite rapid progress in LLM agents," citing (1) narrow scope — "current benchmarks rely on explicit tool specifications, shallow few-step workflows, and isolated domain operations," inadequate for "real-world scenarios requiring complex objectives, grounding responses in intermediate tool outputs, and orchestrating cross-domain workflows"; (2) limited tool diversity — benchmarks like "MCP-RADER and MCPEval cover only a few servers with at most several dozen tools"; (3) fragmented evaluation — prior benchmarks "evaluate tool use, memory, and other components separately"; (4) inadequate failure diagnostics — "single-turn benchmark formats... do not capture multi-turn failures such as tool chaining, recovery from earlier mistakes, or state updates across interactions"; and a call that future benchmarks "should include retrieval corpora, evidence requirements, tool-use traces, escalation scenarios, adversarial documents, and operational constraints" — [search synthesis citing MCP-Bench (arXiv:2508.20453), ToolFailBench, AgentBoard, and related benchmark papers]
- The **chance-corrected tool-count paper** makes an explicit methodological critique: existing benchmarks "were not designed to evaluate search depth" (i.e., how many tools should be retrieved/exposed before selection), which is exactly the efficiency-accuracy tradeoff variable — and explicitly calls for "a purpose-built benchmark with controlled difficulty distributions" to fill this gap — [How Many Tools Should an LLM Agent See?, arXiv:2605.24660](https://arxiv.org/html/2605.24660v1)
- "The 99% Success Paradox: When Near-Perfect Retrieval Equals Random Selection" (title alone is a strong critical claim) appears to argue that near-ceiling retrieval/success metrics on current benchmarks can be statistically indistinguishable from random selection under certain conditions — i.e., current success-rate metrics may not actually measure meaningful tool-selection skill — [arXiv:2605.18857](https://arxiv.org/pdf/2605.18857) *(title and framing found via search; full text not fetched — see Gaps)*
- "Benchmarks Are Not Validation: A System-Level View of Financial LLM Applications" argues, at least in its domain, that passing a benchmark is not equivalent to system-level validation for real deployment — a direct position-paper-style critique of over-reliance on benchmark scores — [arXiv:2607.28840](https://arxiv.org/html/2607.28840v1)

### Inferences
- There is a identifiable, citable line of critique — spanning benchmark-defect audits (BFCL), scope/diversity critiques (MCP-Bench and peers), and metric-validity critiques (the "99% paradox" title) — that converges on the same claim relevant to this workshop paper: current tool-use benchmarks measure task-completion accuracy under a fixed, usually-small tool-exposure/complexity setting, and do not have an established methodology for measuring the accuracy achieved *per unit of cost* (tokens, latency, tool calls) across varying tool-set sizes/difficulty — which is precisely the "optimal way to handle tasks without dropping accuracy" framing the researcher is targeting. This is a strong, multi-source-supported gap to open the paper with.
