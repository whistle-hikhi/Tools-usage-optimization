# Tool Selection and Routing Strategies in LLM Agent Systems

## How do retrieval-augmented tool selection approaches work when there are hundreds/thousands of candidate tools, and how do they affect accuracy vs. naive full-context tool listing?

### Takeaway
Embedding/retrieval-based tool selection (ToolBench's API retriever, Toollery, SkillRouter-style benchmarks) is now the standard way to scale tool-using agents past the small number of tools (~10–50) that fit reliably in a prompt; across multiple 2024–2026 papers, retrieval-first pipelines cut prompt/token volume by 10–40x while holding accuracy flat or improving it relative to dumping all tool specs into context, but naive single-stage dense retrieval still degrades predictably as the tool library grows into the tens of thousands, motivating a second wave of compression/reranking/diversity methods.

### Cited Findings
- ToolBench (ToolLLM) trains a Sentence-BERT-based dense "API retriever" that encodes the instruction and each API document into embeddings and ranks APIs by embedding similarity; it is trained via contrastive learning with relevant APIs as positives and sampled APIs as negatives, evaluated with NDCG, and compared against BM25 and OpenAI `text-embedding-ada-002` baselines — [ToolLLM: Facilitating Large Language Models to Master 16000+ Real-world APIs, arXiv:2307.16789](https://arxiv.org/pdf/2307.16789); [GitHub OpenBMB/ToolBench](https://github.com/openbmb/toolbench)
- On ToolBench's own benchmark, ToolLLaMA+DFSDT using the full ground-truth ("oracle") API set achieved a 60.0% pass rate / 55.2% win rate, while ToolLLaMA+DFSDT+Retriever (retrieving from the full 16,000+ API pool rather than using oracle APIs) achieved a 63.1% pass rate — i.e., retrieval-based selection matched or slightly exceeded oracle-API performance despite searching a much larger space, while ToolLLaMA+DFSDT with the full candidate set and no retrieval limiting achieved 66.7% pass rate / 67.3% win rate — [ToolLLM, arXiv:2307.16789](https://arxiv.org/pdf/2307.16789) (secondary summary via search)
- Toollery (2026), a training-free "candidate compression" framework, generates ~3 synthetic user-intent queries per tool/skill offline to build a retrieval index, then at inference retrieves a compact top-k set before handing it to the LLM for final selection; compared against raw BM25/dense retrieval, full-library prompting, and a "Re-Invoke" query-expansion baseline — [Toollery: Scaling LLM Agents to Thousands of Skills and Tools, arXiv:2609.22218](https://arxiv.org/html/2609.22218v1)
- On the SkillRouter benchmark (~79K capabilities), Toollery improved Hit@1 from 0.553 to 0.920 and Recall@10 from 0.571 to 0.942 versus raw embedding retrieval; full-library prompting required ~43.1M tokens versus 27.7K tokens for Toollery's top-10 retrieval — [Toollery, arXiv:2609.22218](https://arxiv.org/html/2609.22218v1)
- On BFCL-V4 (457 tools), Toollery maintained AST accuracy at 0.837 vs. 0.770 for full-library prompting, while cutting input tokens from 84.1K to 2.1K and latency from 11.8s to 1.6s — [Toollery, arXiv:2609.22218](https://arxiv.org/html/2609.22218v1)
- On a "Smart Cockpit" dataset (220 tools), Toollery improved exact tool-set accuracy from 0.163 to 0.268 and FullCoverage@10 from 0.224 to 0.381, while reducing input tokens from 35.2K to 1.9K — [Toollery, arXiv:2609.22218](https://arxiv.org/html/2609.22218v1)
- General framing from industry/applied literature: "As LLM agents are exposed to hundreds to tens of thousands of skills, tools, and API functions, full-library prompting becomes costly, slow, and less reliable," and intelligent tool retrieval "can triple tool invocation accuracy while reducing prompt length in half" — [Red Hat Emerging Technologies, Tool RAG: The Next Breakthrough in Scalable AI Agents](https://next.redhat.com/2025/11/26/tool-rag-the-next-breakthrough-in-scalable-ai-agents/)
- Routing/retrieval accuracy does not scale gracefully by default: per a survey-style synthesis, "routing accuracy decays logarithmically with library size, with errors progressing from local skill competition to cross-family drift and capture by overly general 'black-hole skills'" — [search synthesis citing SkillRouter-adjacent literature](https://arxiv.org/pdf/2609.05824) (note: this specific decay-pattern language could not be independently verified inside the fetched paper text — see Gaps)
- "Beyond Top-k Skill Retrieval: Diversity-Aware Skill Routing for LLM Agents" proposes Diverse Skill Routing (DSR), using Determinantal Point Processes with a query-residual diversity kernel to reduce redundancy among retrieved candidates (independent top-k retrieval can return redundant shortlists when multiple skills have similar descriptions). On the SkillRouter benchmark (75 queries, ~80K skills): DSR improves Recall@20 from 0.754 to 0.768 and FullCoverage@20 from 0.560 to 0.573 overall; for multi-skill queries specifically, Recall@20 improves from 0.704 to 0.739 and FullCoverage@20 from 0.458 to 0.492 (rising to 0.551 at k=50) — [Beyond Top-k Skill Retrieval, arXiv:2609.05824](https://arxiv.org/html/2609.05824v1)
- Gorilla (APIBench, ~1,600 ML APIs) introduces "Retriever-Aware Training" (RAT), enabling the fine-tuned LLM to use retrieved API documentation at inference time; with a document retriever attached, Gorilla adapts to test-time API/document changes and substantially reduces hallucinated API usage versus GPT-4/Claude on the same benchmark — [Gorilla: Large Language Model Connected with Massive APIs, arXiv:2305.15334](https://arxiv.org/pdf/2305.15334)
- A growing family of specialized tool-retriever papers (2024–2026) targets specific weaknesses of plain dense retrieval at scale: ToolRetriever (BERT-based, contrastive learning) as the ToolBench baseline; ToolGen (unifying retrieval and calling into one generation step); ToolDreamer (retrieval conditioned on LLM-hallucinated/hypothetical tool descriptions, HyDE-style); PORTS (preference-optimized retrievers trained directly against downstream task success rather than lexical/semantic similarity alone); ToolRerank (hierarchy-aware reranking); Tool2Vec (four-stage fine-tuning: semantic, collaborative, list-wise, contrastive learning) — [search synthesis](https://arxiv.org/pdf/2409.02141), [ToolDreamer arXiv:2510.19791](https://arxiv.org/pdf/2510.19791), [PORTS arXiv:2607.05441](https://arxiv.org/pdf/2607.05441), [ToolRerank arXiv:2403.06551](https://arxiv.org/pdf/2403.06551)

### Inferences
- The field has converged on a two-stage pattern — cheap retrieval/compression narrows thousands of tools to a short candidate list, then the LLM makes the final choice among that list — because this simultaneously controls token/latency cost (the dominant efficiency lever) and avoids the accuracy collapse that comes from overloading context with irrelevant tool specs.
- As libraries scale from hundreds to tens of thousands of tools, single-stage embedding retrieval alone becomes insufficient (redundant/near-duplicate candidates, cross-family confusion), which is why 2025–2026 papers increasingly add diversity-aware reranking (DSR/DPP), query synthesis (Toollery, ToolDreamer), or preference/outcome-based retriever training (PORTS) on top of plain dense retrieval.
- The ToolLLM result that retrieval-based selection can match or exceed "oracle" (ground-truth) API provisioning is notable: giving the LLM too many correct-but-unranked options can itself hurt reasoning, so a well-tuned retriever is not just a cost-saving filter but can also be an accuracy aid by reducing distractor tools in context.

## What learned tool-routing or tool-selection models exist (small classifier/router models that pick a tool before invoking a larger LLM, hierarchical delegation)?

### Takeaway
Two distinct "routing" literatures exist and are sometimes conflated: (1) LLM-model routers that pick which model (not tool) handles a query (e.g., RouteLLM) to save cost, and (2) tool/skill routers that pick which tool(s) from a large catalog to expose to the LLM, which increasingly use trained rerankers, preference-optimized retrievers, or lightweight classifiers rather than the main LLM itself, specifically to avoid the latency/cost of a separate LLM "pre-flight" call.
- A cross-cutting design principle from the model-routing literature (directly transferable to tool-routing): a two-stage router where the first stage is deterministic (features like prompt length, output-shape, code markers, language, safety category, computed without any model call) resolves obvious cases immediately, reserving learned/LLM-based routing for ambiguous cases — because "adding 500ms of LLM inference on top of 200–2,000ms model inference increases total latency by 25–250%" — [getmaxim.ai / orq.ai synthesis on LLM routers](https://orq.ai/blog/llm-router)
- RouteLLM frames model routing as a preference-prediction problem: a lightweight router is trained on human preference data to predict whether a query needs a strong (expensive) LLM or can be handled by a weak (cheap) one, reducing inference cost while preserving response quality — [search synthesis, RouteLLM](https://dzone.com/articles/low-latency-llm-routing)
- GraphRouter models LLM selection as a graph-based routing problem rather than a flat classifier — [GraphRouter: A Graph-based Router for LLM Selections, arXiv:2410.03834](https://arxiv.org/pdf/2410.03834)
- MasRouter extends routing to multi-agent systems specifically, learning to route among LLMs/agents within a multi-agent system rather than a single model call — [MasRouter: Learning to Route LLMs for Multi-Agent Systems, arXiv:2502.11133](https://arxiv.org/pdf/2502.11133)
- "Outcome-Aware Tool Selection for Semantic Routers" explicitly targets latency-constrained tool routing that avoids LLM inference in the routing decision itself — [arXiv:2603.13426](https://arxiv.org/pdf/2603.13426)
- "Latency-Quality Routing for Functionally Equivalent Tools in LLM Agents" addresses the case where multiple tools accomplish the same task with different latency/quality tradeoffs, proposing a routing mechanism (framed around bandit-style/probabilistic selection per secondary extraction) to dynamically pick among functionally-equivalent tool implementations rather than treating tool selection as a single correct-answer classification problem — [arXiv:2605.14241](https://arxiv.org/pdf/2605.14241)
- Hierarchical delegation (a planner LLM assigning whole subtasks to specialist tool-using agents, rather than picking individual tools) is treated as a distinct efficiency lever: "by delegating complex subtasks to agent tools, the planner can operate over a shorter and more structured action space, and instead of explicitly invoking individual tools, the planner delegates entire subtasks to a single agent tool" — [HTAA: Hybrid Toolset Agentization & Adaptation, arXiv:2604.10917](https://arxiv.org/html/2604.10917)
- AgentOrchestra implements this hierarchical pattern concretely via a "Tool-Environment-Agent (TEA) protocol": a central planning agent decomposes complex objectives and delegates sub-tasks to specialized sub-agents while maintaining a global perspective across execution — [AgentOrchestra, arXiv:2506.12508](https://arxiv.org/html/2506.12508v4)
- "Agent-as-Tool" studies the hierarchical decision problem of when a planner should call a raw tool directly versus delegate to another agent-as-tool — [arXiv:2507.01489](https://arxiv.org/pdf/2507.01489)

### Inferences
- The strongest argument against using a full LLM call as the "router" for tool selection is latency compounding (every extra LLM round-trip is 200ms–2s), which is pushing both the model-routing and tool-routing sub-literatures toward the same solution: cheap, trained, non-generative classifiers/rerankers/embedding similarity for the coarse decision, with the expensive LLM reserved for final disambiguation or execution.
- Hierarchical delegation (planner → specialist agent, each agent owning a small tool subset) is functionally a form of tool routing at a coarser grain: it reduces the "action space" the top-level planner must search, trading a flat N-tool selection problem for a shallow tree of smaller selection problems — this is the same complexity-reduction logic as retrieval-based tool shortlisting, just organized around agent boundaries instead of a retrieval index.

### Gaps
- No single paper was found that benchmarks a dedicated, standalone "tool-router classifier" (analogous to RouteLLM for models) head-to-head against both full-context tool listing AND embedding retrieval, with efficiency and accuracy numbers in one table — the literature currently treats this as either a retrieval problem (previous section) or folds it into multi-agent delegation (next section). This is a candidate gap/novelty angle for the workshop paper.

## What approaches exist for multi-agent delegation of tool use, and how do they manage efficiency?

### Takeaway
AutoGen, MetaGPT, and CAMEL represent three different delegation philosophies — conversational/dynamic (AutoGen), structured role-pipeline with SOPs (MetaGPT), and role-play/inception-prompted cooperation (CAMEL) — and empirical head-to-head benchmarking (e.g., MegaAgent's comparisons) shows large, task-dependent differences in wall-clock time, number of agents used, and token consumption, with no universal winner; efficiency in hierarchical multi-agent systems is governed less by the framework and more by delegation correctness (avoiding misrouted subtasks and duplicated worker effort).

### Cited Findings
- "AutoGen and CAMEL explore flexible multi-agent dialogue, the former through conversable agents with multi-turn exchange and the latter through inception-prompted role-playing. MetaGPT takes a more structured approach, encoding Standardized Operating Procedures into role-specialized assembly-line pipelines" — [emergentmind.com, Camel and AutoGen: Advanced Agentic Frameworks](https://www.emergentmind.com/topics/camel-and-autogen-frameworks)
- AutoGen is a "conversational multi-agent framework in which agents negotiate task decomposition and tool invocation dynamically" — [AutoGen: Enabling Next-Gen LLM Applications via Multi-Agent Conversation, arXiv:2308.08155](https://arxiv.org/pdf/2308.08155)
- MetaGPT "assign[s] software-engineering roles — product manager, architect, engineer — to distinct agents coordinated via structured output schemas" — [search synthesis](https://aiengineeringinsider.substack.com/p/autogen-crewai-and-multi-agent-orchestration)
- Common orchestration patterns identified across the literature: "single agent for simple tool-use workflows, planner–executor for multi-step decomposition, supervisor–worker for controlled delegation, and crew/team-based agents for role-specialized collaboration" — along with named efficiency risks of hierarchical designs: "incorrect delegation by the manager agent, workers duplicating effort, inconsistent context across agents, and token cost growth" — [search synthesis](https://aiengineeringinsider.substack.com/p/autogen-crewai-and-multi-agent-orchestration)
- Comparative benchmarking (MegaAgent paper) found in a game-playing scenario AutoGen used 2 agents and finished in 180 seconds (90s/agent), while MetaGPT used 6 agents and finished in 480 seconds (80s/agent); for a code-generation task, AutoGen produced an outline with 1 agent in 40 seconds while MetaGPT produced a full Python program with 6 agents in 580 seconds — illustrating that MetaGPT's structured pipeline uses more agents/time but can produce more complete output — [MegaAgent, ACL Findings 2025, aclanthology.org/2025.findings-acl.259.pdf](https://aclanthology.org/2025.findings-acl.259.pdf) (via secondary synthesis)
- Token-level accounting example from MetaGPT's own pipeline stages: planning stage used 42,947 input + 12,347 output tokens (55,294 total); task-solving stage used 1,098,573 input + 55,022 output tokens (1,153,595 total); merging stage used 22,099 input + 1,493 output tokens (23,592 total) — showing the "task-solving" (tool-execution) phase dominates token cost by roughly 20x over planning — [secondary synthesis citing MegaAgent-style benchmarking](https://aclanthology.org/2025.findings-acl.259.pdf)
- In one reported comparison on MBPP/HumanEval code-benchmarks, MetaGPT scored 81.7%/82.3% while AutoGen scored 85.3%/85.9% — [search synthesis; original primary source not independently verified, see Gaps]
- AgentOrchestra's hierarchical planner explicitly aims at efficiency-via-structure: "a central planning agent that decomposes complex objectives and delegates sub-tasks to a team of specialized agents... based on their expertise, while maintaining a global perspective throughout execution" — [arXiv:2506.12508](https://arxiv.org/html/2506.12508v4)

### Inferences
- Across frameworks, the dominant efficiency cost is not the number of agents per se but how well subtasks are routed/decomposed: misrouted delegation and duplicated worker effort (flagged explicitly in the orchestration-pattern synthesis) appear to be the primary failure modes driving token/time blowups, more so than the choice of AutoGen vs. MetaGPT vs. CAMEL as a framework.
- The MetaGPT token breakdown (task-solving stage ~20x the token cost of planning) supports a design implication directly relevant to tool-selection optimization: investment in better upfront planning/tool-routing (cheap) has outsized leverage over the expensive downstream execution/tool-call phase, reinforcing the case for retrieval/routing investments made earlier in this report.

### Gaps
- Could not independently verify the MBPP/HumanEval percentage comparison between MetaGPT and AutoGen against a primary source — it surfaced only via secondary aggregation; the report-writer should treat it as unconfirmed or seek the original benchmark paper.
- Could not directly extract CAMEL's own efficiency numbers (vs. AutoGen/MetaGPT) from a primary source within the tool-call budget; only descriptive characterization ("role-playing," "autonomous cooperation") was confirmed.
- No primary source was found that isolates the efficiency effect of "tool delegation" specifically (as opposed to general multi-agent task delegation) within AutoGen/MetaGPT/CAMEL — most available efficiency numbers are at the whole-task level (total tokens/time), not decomposed into tool-call counts specifically.

## What caching/memoization/reuse-of-tool-results strategies exist to avoid redundant tool calls?

### Takeaway
Semantic caching of tool/API outputs — going beyond exact-match caching to embedding-similarity matching with a validation stage — delivers some of the largest measured efficiency gains in this entire research scope (3–6x throughput, up to 92% reduction in external API calls, 85–95% cache hit rates in some workloads), while simpler exact-argument memoization (hashing tool name + normalized arguments) is a lower-complexity but still effective technique against literal redundant calls within a session; separately, experiential/skill memories (e.g., Voyager's skill library) reuse entire successful tool-use trajectories across tasks rather than individual call results.

### Cited Findings
- GPTCache "intercepts LLM calls, computes embeddings for queries, and returns cached responses when similarity exceeds a threshold," supporting multiple embedding backends and vector stores (FAISS, Milvus); semantic caching broadly is reported to cut LLM inference costs 30–70% by reusing similar-query results — [dataaihub.co / spheron.network synthesis on GPTCache](https://www.spheron.network/blog/semantic-cache-llm-inference-gpu-cloud/)
- Asteria (2025) is a semantic-aware cross-region caching system specifically for agentic LLM tool access. Motivation: "external data retrieval consistently constitutes around 40%-50% of the total execution time," and a service with 100M monthly users at 10 tool calls/query could incur "$150,000 in daily API fees"; traditional exact-match caching fails because "even minor wording changes trigger cache misses and unnecessary remote calls" — [Asteria, arXiv:2509.17360](https://arxiv.org/html/2509.17360v1)
- Asteria's mechanism: Semantic Elements (query + response + metadata including embeddings, access frequency, latency, cost, and a "staticity score") indexed via a two-stage "Semantic Retrieval Index (Sine)" — an ANN index for candidate matching (similarity threshold τ_sim = 0.9) followed by a lightweight 1B-parameter LLM "Semantic Judger" that validates true semantic equivalence (threshold τ_lsm = 0.9) before registering a cache hit, because "vector proximity often fails to capture true semantic equivalence" (example: "apple nutrition facts" vs. "Apple stock price analysis") — [Asteria, arXiv:2509.17360](https://arxiv.org/html/2509.17360v1)
- Asteria measured results: 3.6x throughput increase on the Musique search-workload dataset, 3.8x on trend-driven workloads, 20% on coding tasks, and 5.7x under high-concurrency request rates; cache hit rates reached over 85% on search workloads (vs. under 20% for exact-match caching) and nearly 95% on trend-driven workloads; single-request latency dropped from 1.08s to 0.61s (eliminating a 0.48s external-retrieval bottleneck, leaving only 0.05s local cache+validation overhead); external API calls were reduced 92% (1,300 → 103 calls) in one scenario; overall the system achieved 6x more throughput per dollar than a vanilla (uncached) baseline, with total operational cost of $76.64 vs. $158.50 for a comparable two-GPU uncached approach; accuracy was preserved as "virtually identical to non-cached baseline" — notably, naive ANN-only caching (without the semantic-judger validation step) showed meaningful accuracy drops (e.g., 0.69 vs. 0.79 on StrategyQA), underscoring that similarity-only caching can silently corrupt correctness — [Asteria, arXiv:2509.17360](https://arxiv.org/html/2509.17360v1)
- Lower-tech exact/argument-hash memoization is also documented as practically significant: one reported production anti-pattern showed "800 calls to a geocoding tool for only 40 unique addresses (20 calls per address on average), with 760 of those calls being duplicates," attributed to LLMs not tracking their own tool-call history at the argument level; a per-turn or per-session registry hashing (tool_name + normalized_args) → output is proposed as the fix — [jsmanifest.com, Claude Code Tool Result Caching in 2026](https://jsmanifest.com/claude-code-tool-result-caching-2026); [dev.to, LRU Memoization for Agent Tool Calls](https://dev.to/mukundakatta/lru-memoization-for-agent-tool-calls-with-tool-result-cache-28on)
- In long-horizon coding-agent sessions, tool-result caching for repeated file reads/shell commands is reported to cut token costs 40–60% in multi-hour workflows, and for batch processing where a field has far fewer unique values than items (e.g., 1,000 items, 50 unique values), caching cuts API calls by up to 95% — [jsmanifest.com](https://jsmanifest.com/claude-code-tool-result-caching-2026)
- "Don't Break the Cache: An Evaluation of Prompt Caching for Long-Horizon Agentic Tasks" evaluates prompt-caching behavior (a related but distinct mechanism from tool-result caching — caching the KV/prefix state rather than the semantic output) specifically in long agent sessions — [arXiv:2601.06007](https://arxiv.org/pdf/2601.06007)
- "ToolCaching: Towards Efficient Caching for LLM Tool-calling" proposes caching specifically for tool-calling and is benchmarked against general-purpose cache-replacement baselines including TinyLFU, CACA, GLCache, SegCache, and P4LRU, and references "LLM-dCache" as a related tool-augmented caching optimization — [arXiv:2601.15335](https://arxiv.org/pdf/2601.15335) (exact numeric results not extractable — see Gaps)
- "SemanticALLI: Caching Reasoning, Not Just Responses, in Agentic Systems" extends semantic caching beyond final outputs to intermediate reasoning traces in agentic systems — [arXiv:2601.16286](https://arxiv.org/pdf/2601.16286) (details not extracted within budget — see Gaps)
- Separately from call-level caching, Voyager's "ever-growing skill library of executable code" stores successful tool-use programs indexed by natural-language description for retrieval and reuse on related future tasks; ablating the skill library caused a 15.3x loss in tech-tree milestone speed in Minecraft, demonstrating that experiential skill-reuse (as opposed to raw output caching) was the dominant driver of the agent's performance — [Voyager: An Open-Ended Embodied Agent with Large Language Models (secondary synthesis), arXiv:2305.16291](https://www.emergentmind.com/papers/2305.16291)

### Inferences
- The semantic-caching literature converges on a common two-stage design (fast approximate match via embeddings + a stricter validator before confirming a hit), exactly mirroring the two-stage pattern seen in tool retrieval (cheap shortlist + precise final check) — suggesting this "coarse-then-precise" pattern is a general efficiency primitive across tool selection, tool-result reuse, and model routing alike.
- The scale of the Asteria cost numbers ($150K/day hypothetical exposure, 92% call reduction, 6x throughput/dollar) indicates caching/reuse strategies can be the single highest-leverage efficiency intervention in tool-heavy agent deployments — larger in relative impact than the token-reduction gains reported for retrieval-based tool selection, though the two are complementary (retrieval reduces which tools are considered; caching reduces how often a chosen tool is actually re-executed).
- Naive embedding-only caching risking silent accuracy corruption (Asteria's StrategyQA ablation, 0.69 vs 0.79) is an important caveat for any workshop paper proposing semantic tool-call caching: a validation/judger stage is not optional overhead but materially protects correctness.

### Gaps
- Could not extract exact quantitative results from "ToolCaching" (arXiv:2601.15335) or "SemanticALLI" (arXiv:2601.16286) due to PDF binary-extraction failures in the WebFetch pipeline; both appear to be directly on-topic and are strong candidates for the report-writer or researcher to re-fetch via a different extraction path (e.g., ar5iv.org HTML mirror, or downloading and parsing locally).
- No source quantified the precise overhead/break-even point for session-level exact-match memoization (only a qualitative note that "cache creation incurs overhead on the first request, only amortized if subsequent requests benefit") — a gap for anyone wanting exact ROI thresholds.

## What is the measured impact of these selection/routing strategies on both efficiency (calls, latency, tokens) and task accuracy?

### Takeaway
Measured results across the surveyed papers are directionally consistent: tool retrieval/compression and semantic caching both report large efficiency wins (order-of-magnitude token/API-call reductions, multi-x throughput/latency gains) typically paired with accuracy that is flat-to-improved relative to naive baselines, provided a validation/reranking/judger stage is included — but losing that validation stage (plain similarity matching alone) measurably hurts accuracy, and the specific magnitude of gains is highly benchmark-dependent (ranging from ~2x to ~6x across different systems and workloads).

### Cited Findings
See the consolidated numeric results already cited above; summarized side-by-side for convenience:
- Tool retrieval (Toollery) on SkillRouter (~79K capabilities): Hit@1 0.553→0.920, Recall@10 0.571→0.942, tokens 43.1M→27.7K (full-library vs. top-10 retrieval) — [arXiv:2609.22218](https://arxiv.org/html/2609.22218v1)
- Tool retrieval (Toollery) on BFCL-V4 (457 tools): AST accuracy 0.770 (full-library)→0.837 (retrieval), tokens 84.1K→2.1K, latency 11.8s→1.6s — [arXiv:2609.22218](https://arxiv.org/html/2609.22218v1)
- Diversity-aware routing (DSR) on SkillRouter (~80K skills, multi-skill queries): Recall@20 0.704→0.739, FullCoverage@20 0.458→0.492 (0.551 at k=50) over plain top-k retrieval — [arXiv:2609.05824](https://arxiv.org/html/2609.05824v1)
- ToolLLM retriever vs. oracle APIs: 63.1% vs. 60.0% pass rate (retriever slightly ahead of oracle, despite searching 16,000+ APIs vs. a hand-given correct set) — [arXiv:2307.16789](https://arxiv.org/pdf/2307.16789) (secondary summary — see Gap above)
- Semantic caching (Asteria) for tool-access: 3.6–5.7x throughput depending on workload, 85–95% hit rates vs. <20% for exact-match, 92% reduction in external API calls, 6x throughput-per-dollar, accuracy "virtually identical" to uncached baseline when a semantic judger is included (vs. a measurable accuracy drop, e.g. 0.69 vs. 0.79 on StrategyQA, with ANN-only matching) — [arXiv:2509.17360](https://arxiv.org/html/2509.17360v1)
- Session-level exact-match tool-call memoization: up to 95% reduction in redundant API calls in high-duplication scenarios (e.g., 760 of 800 geocoding calls were exact duplicates); 40–60% token cost reduction in long coding-agent sessions — [jsmanifest.com](https://jsmanifest.com/claude-code-tool-result-caching-2026)
- Experiential skill-memory reuse (Voyager): 15.3x speed-up in task-milestone completion attributable to the reusable skill library versus an agent without it — [arXiv:2305.16291 (secondary synthesis)](https://www.emergentmind.com/papers/2305.16291)
- Multi-agent delegation (MetaGPT vs. AutoGen, task-dependent): roughly 2.7x more wall-clock time and 3x more agents for MetaGPT's structured pipeline vs. AutoGen's conversational approach in one code-generation task (580s/6 agents vs. 40s/1 agent), with MetaGPT's task-solving phase consuming ~20x the tokens of its own planning phase — [secondary synthesis citing MegaAgent, aclanthology.org/2025.findings-acl.259.pdf](https://aclanthology.org/2025.findings-acl.259.pdf)

### Inferences
- A consistent pattern across retrieval, routing, and caching papers is that efficiency gains (10x–100x in token/call volume) are typically much larger in relative magnitude than the accompanying accuracy changes (usually single-digit percentage-point shifts, often positive) — suggesting that, in well-designed systems, the main argument for these techniques is cost/latency, with accuracy as a secondary (and often favorable) side effect rather than a tradeoff.
- The single clearest "accuracy can suffer" finding in this research scope is specifically about omitting a validation/reranking stage (Asteria's ANN-only ablation; the general literature's note that embedding retrieval alone misses true semantic equivalence) — this is the most citable example of a concrete selection/caching mechanism degrading accuracy in a measured, reproducible way, as opposed to a purely hypothetical risk.

### Gaps
