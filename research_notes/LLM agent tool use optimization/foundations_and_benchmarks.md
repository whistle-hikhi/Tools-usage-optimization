# Foundations of LLM Tool/Function Calling and Its Benchmarking

## What are the core technical approaches to LLM function/tool calling?

### Takeaway
Tool-calling approaches split into four families that build on each other chronologically: (1) self-supervised fine-tuning to insert API calls into text (Toolformer), (2) prompt-based interleaved reasoning+acting with text parsing (ReAct), (3) fine-tuned specialist models for API/tool generation (Gorilla, ToolLLaMA, NexusRaven), and (4) native structured-output / constrained-decoding function-calling APIs now offered by all major LLM providers, which guarantee schema-valid JSON via grammar-constrained decoding rather than free-text parsing.

### Cited Findings
- **Toolformer** (Schick et al., Meta AI, submitted Feb 9 2023, arXiv:2302.04761) trains a model to decide "which APIs to call, when to call them, what arguments to pass, and how to best incorporate the results into future token prediction" via a self-supervised procedure requiring only a handful of demonstrations per API; it incorporates a calculator, two search engines (Wikipedia, a QA system), a translation system, and a calendar tool, learned "in a self-supervised way" without large-scale human annotation. — [arXiv:2302.04761](https://arxiv.org/abs/2302.04761)
- **ReAct** (Yao et al., submitted Oct 2022, arXiv:2210.03629) is a prompting paradigm, not a fine-tuned model: it generates reasoning traces interleaved with task-specific actions in the same text stream, where "reasoning traces help the model induce, track, and update action plans... while actions allow it to interface with and gather additional information from external sources" such as a Wikipedia API; demonstrated on HotpotQA, FEVER, text games, and web navigation. — [arXiv:2210.03629](https://arxiv.org/abs/2210.03629)
- **Gorilla** (Patil et al., UC Berkeley/Microsoft Research, submitted May 2023, arXiv:2305.15334) is a LLaMA-based model fine-tuned specifically to write correct API calls; it is reported to surpass GPT-4 on this narrow task and, "when combined with a document retriever," adapts to test-time API/documentation changes and substantially reduces hallucinated API usage compared with directly-prompted LLMs. — [arXiv:2305.15334](https://arxiv.org/abs/2305.15334)
- **ToolLLM / ToolBench / ToolLLaMA** (Qin et al., submitted July 2023, arXiv:2307.16789, ICLR 2024 spotlight): ToolBench is an instruction-tuning dataset built by scraping 16,464 real-world RapidAPI APIs and using ChatGPT to automatically generate instructions and valid multi-step solution paths; ToolLLaMA is LLaMA-2-7B fine-tuned on this data, augmented with a neural API retriever so it can generalize to unseen APIs; reported to perform "comparable to ChatGPT." — [arXiv:2307.16789](https://arxiv.org/abs/2307.16789); [GitHub](https://github.com/openbmb/toolbench)
- ToolLLM introduces **DFSDT (Depth-First Search-based Decision Tree)**, a planning algorithm that generalizes ReAct: instead of a single linear reasoning chain, the model explores multiple candidate reasoning/action nodes and can backtrack ("retract steps") when a path fails, using a pre-order-traversal variant of DFS to balance solution quality against the number of API calls (cost). This directly targets ReAct's error-propagation and limited-exploration weaknesses. — [arXiv:2307.16789](https://arxiv.org/abs/2307.16789)
- **NexusRaven / NexusRaven-V2** (Nexusflow) is an open-source, commercially-permissive function-calling LLM built on the CodeLLaMA-13B lineage, trained via "multi-step refinement" data curation that explicitly avoids distilling from GPT-4 outputs (for licensing reasons); NexusRaven-V2 supports single calls, parallel (disconnected) calls, and nested calls where one function's argument is itself the output of another call, and is reported to surpass GPT-4 by up to 7% in function-calling success on human-generated nested/composite-call tasks. — [OpenReview](https://openreview.net/pdf?id=5lcPe6DqfI); [GitHub](https://github.com/nexusflowai/NexusRaven-V2)
- **Native provider function-calling APIs** (OpenAI, and by extension Anthropic/Google equivalents) work by the developer passing a `tools` parameter with each function's `name`, `description`, and a JSON Schema for arguments; the model does not execute anything itself — it returns a structured `tool_call` object (e.g., `{"name": "get_stock_price", "arguments": {"ticker": "AAPL"}}`), the calling application executes the function and returns results, and the model synthesizes a grounded final answer. "The model never touches your API keys, never executes code on your server — it just requests tool execution." — [OpenAI function calling docs](https://developers.openai.com/api/docs/guides/function-calling)
- **Constrained / grammar-based decoding** underlies modern structured-output and function-calling guarantees: JSON Schemas (or Pydantic models) are compiled into finite-state machines or context-free grammars; at each decoding step the FSM/CFG determines which tokens are permissible and impermissible-token logits are set to −∞, making schema violations unsamplable. Libraries/engines named: Outlines (JSON Schema/Pydantic → CFG), xgrammar and Outlines integrated into serving frameworks SGLang and vLLM. "Function calling is a specialization of JSON-schema constrained decoding where the schema names a tool to invoke," and this is now "the default for LLM-to-program interfaces," with OpenAI, Anthropic, Google, and open-source serving stacks all exposing native JSON-schema constraints. — [ZeroEntropy: Constrained Decoding](https://zeroentropy.dev/concepts/constrained-decoding/); [dev.to structured output overview](https://dev.to/tech_nuggets/structured-output-from-llms-json-mode-function-calling-and-grammar-constrained-decoding-355d)
- A 2026 empirical study, "Constraint Tax in Open-Weight LLMs" (arXiv:2606.25605), documents that structured-output constraints can *suppress* a model's tool-calling behavior in open-weight LLMs — i.e., forcing strict JSON-schema decoding is not a free lunch and can trade off against the model's willingness/ability to invoke tools correctly. — [arXiv:2606.25605](https://arxiv.org/pdf/2606.25605)

### Inferences
- The field has converged on a layered stack: (a) base model capability for argument reasoning/planning (trained via Toolformer-style self-supervision or instruction-tuned corpora like ToolBench), (b) a planning/search strategy over tool-call sequences (ReAct → DFSDT → more recent multi-agent/reflection variants), and (c) an inference-time enforcement layer (grammar-constrained decoding) that guarantees syntactic validity independent of model quality. A workshop paper on "tool-use optimization" likely needs to position its contribution against all three layers, since gains at one layer (e.g., better constrained decoding) do not substitute for gains at another (e.g., correct argument semantics or multi-step planning).
- The "native function-calling API" approach and "ReAct-style text parsing" are not mutually exclusive history — native APIs essentially productized and hardened the ReAct-style tool-call pattern by adding schema validation at decode time, removing the need for brittle regex/text parsing of the model's free-form output.

- Did not verify current (2025/2026) adoption details of Anthropic's and Google's native tool-use/function-calling API internals (only OpenAI's mechanism was directly sourced); the general mechanism is almost certainly the same (schema-in, structured JSON-out) but provider-specific implementation notes were not fetched.

## What are the major benchmarks, what do they test, what are their metrics, and what are current trends (2024–2026)?

### Takeaway
The benchmark landscape evolved from single-turn, single-tool, rule-matched benchmarks (API-Bank, Gorilla/APIBench, early ToolBench, BFCL v1) toward multi-turn, multi-tool, state-tracking, and robustness/stability-focused benchmarks (BFCL v2/v3/v4, StableToolBench, NESTFUL, Seal-Tools, T-Eval, MetaTool, RoTBench), with a 2024–2026 wave of papers explicitly built to fix contamination and unrealistic-task problems in the earlier generation (FuncBenchGen, ComplexFuncBench, ToolRobustBench, HammerBench).

### Cited Findings
- **API-Bank** (arXiv:2304.08244, submitted Apr 2023, EMNLP 2023) is a "runnable evaluation system" with 73 API tools for evaluation and a training set of 1,888 tool-use dialogues spanning 2,138 APIs across 1,000 domains; it evaluates three capabilities — **planning, retrieving, and calling** API tools. Their fine-tuned model Lynx (from Alpaca) "surpasses Alpaca's tool utilization performance by more than 26 pts" and approaches GPT-3.5-level effectiveness; GPT-4 was found to "excel in planning" while GPT-3.5 improved over GPT-3 in tool utilization generally. — [arXiv:2304.08244](https://arxiv.org/abs/2304.08244)
- **Gorilla / APIBench** (arXiv:2305.15334): APIBench contains 1,645 API calls scraped from TorchHub, TensorFlow Hub, and HuggingFace model hubs — i.e., ML model/API-invocation tasks rather than general web APIs. — [HF dataset: gorilla-llm/APIBench](https://huggingface.co/datasets/gorilla-llm/APIBench); [arXiv:2305.15334](https://arxiv.org/abs/2305.15334)
- **ToolBench / ToolLLM / ToolEval** (arXiv:2307.16789): ToolBench itself is built from 16,464 real RapidAPI-sourced APIs. The companion **ToolEval** framework defines two metrics: **Pass Rate** — "the proportion of successfully completing an instruction within limited OpenAI API calls" (i.e., a budgeted task-completion rate), and **Win Rate** — pairwise preference judgments between two solution paths' quality/usefulness, scored by an LLM judge using criteria written as prompts. ToolEval's automatic (ChatGPT-based) judge was validated against human annotators at 87.1% agreement on pass rate and 80.3% agreement on win rate. ToolLLaMA (with DFSDT) "surpasses Text-Davinci-003, Claude-2, and almost performs on par with ChatGPT." A later (2025-era) small-model paper reports a 350M-parameter fine-tuned model reaching 77.55% overall pass rate, outperforming baselines by 47–75 points — illustrating rapid leaderboard progress since 2023. — [arXiv:2307.16789](https://arxiv.org/abs/2307.16789); [ToolEval leaderboard](https://openbmb.github.io/ToolBench/); [arXiv:2512.15943](https://arxiv.org/html/2512.15943v1)
- **StableToolBench** (arXiv:2403.07714, submitted Mar 2024, latest revision Mar 2025) is explicitly a reliability fix for ToolBench: it identifies that real online APIs cause **non-stationary behavior** (endpoints going offline, quota limits, response-format drift) and **randomness in evaluation**, and addresses this with (1) a virtual API server combining a caching system and API simulators, and (2) a "stable evaluation system" that computes "solvable pass and win rates" using GPT-4 as judge "to eliminate randomness during evaluation." — [arXiv:2403.07714](https://arxiv.org/abs/2403.07714); [GitHub](https://github.com/THUNLP-MT/StableToolBench)
- **Berkeley Function-Calling Leaderboard (BFCL)**, now at **v4** (Gorilla project, UC Berkeley): version history per the official leaderboard page — **v1** introduced AST (Abstract Syntax Tree) matching as the core evaluation metric; **v2** added enterprise- and OSS-community-contributed function sets; **v3** added multi-turn interactions and state-based tracking; **v4** (current) adds "holistic agentic evaluation" and real-world data. BFCL distinguishes models with **native function-calling support ("FC")** from those using **prompt-based workarounds**, and reports "Overall Accuracy" as an unweighted average across sub-categories, plus **Cost** (estimated USD for the full benchmark) and **Latency**. Current evaluation is pinned to a specific commit and the `bfcl-eval` PyPI package (e.g., version `2025.12.17`) for reproducibility. — [gorilla.cs.berkeley.edu/leaderboard.html](https://gorilla.cs.berkeley.edu/leaderboard.html); [HF dataset](https://huggingface.co/datasets/gorilla-llm/Berkeley-Function-Calling-Leaderboard)
- BFCL v3 specifically (per secondary synthesis sourced from arXiv:2510.22898 and related 2025 papers) spans four challenge types — **Base, Miss Func, Miss Param, Long Context** — over 4,951 test instances (3,951 single-turn + 1,000 multi-turn), reporting **Abstract Syntax Tree (AST) accuracy** (structural match of generated call vs. ground truth and the function spec: correct function name, required-parameter inclusion, correct parameter types/values), **Executable Function Accuracy (EFA)** (the call is actually executed and its runtime output compared to the expected result), per-turn correctness, and multi-turn logical coherence. — [arXiv:2510.22898](https://arxiv.org/pdf/2510.22898); [EvalScope BFCL-v3 docs](https://evalscope.readthedocs.io/en/v0.17.0/third_party/bfcl_v3.html)
- **T-Eval** (arXiv:2312.14033, ACL 2024) departs from holistic/outcome-only scoring: it "comprehensively decomposes tool utilization into multiple sub-processes, including instruction following, planning, reasoning, retrieval, understanding, and review," evaluating each sub-capability step by step rather than only the final success/failure, using a multi-agent data-generation pipeline verified by human experts for stability. — [arXiv:2312.14033](https://arxiv.org/abs/2312.14033); [GitHub](https://github.com/open-compass/T-Eval)
- **MetaTool / ToolE** (arXiv:2310.03128, ICLR 2024) targets a different question than most benchmarks — not "did the model call the right tool correctly" but "does the model know *whether* to use a tool at all, and *which* one." The ToolE dataset has ~21K user queries mapped to ~43 tools; four subtasks test tool selection among similar choices, in specific scenarios, under reliability concerns, and multi-tool selection. Across 8 popular LLMs tested, "the majority of them still struggle to effectively select tools." — [arXiv:2310.03128](https://arxiv.org/abs/2310.03128)
- **Seal-Tools** (arXiv:2405.08355, NLPCC 2024) is a self-instruct-generated tool-learning dataset emphasizing "hard instances that call multiple tools... among which some are nested tool callings"; it defines three distinct metrics for strict, multi-dimensional evaluation and finds that "current systems are far from perfect" even with fine-tuning. — [arXiv:2405.08355](https://arxiv.org/abs/2405.08355); [GitHub](https://github.com/fairyshine/Seal-Tools)
- **AgentBench** (arXiv:2308.03688, submitted Aug 2023) is a broader agent benchmark (not tool-calling-specific) spanning 8 environments (OS, DB, knowledge graph, digital card game, lateral-thinking puzzles, web shopping/browsing, etc.); it evaluates 27 LLMs on multi-turn interacting tasks estimated to need 5–50 turns to solve, finding "a significant disparity" between top commercial LLMs and open-source models ≤70B parameters as agents. — [arXiv:2308.03688](https://arxiv.org/abs/2308.03688)
- **NexusRaven benchmark** (the model's own eval suite) focuses on realistic software/enterprise and cybersecurity use cases, with 65 distinct APIs and 318 total samples, specifically probing single, parallel, and nested function calls. — [llm-stats.com/benchmarks/nexus](https://llm-stats.com/benchmarks/nexus)
- **NESTFUL** (arXiv:2409.03797, 2024) benchmarks **nested sequences of API calls**, i.e., cases where a later call's arguments depend on an earlier call's output — explicitly targeting a gap in single-call benchmarks. — [arXiv:2409.03797](https://arxiv.org/pdf/2409.03797)
- **RoTBench** (arXiv:2401.08326) is a "multi-level benchmark for evaluating the robustness of LLMs in tool learning," probing degradation under perturbed/noisy conditions rather than clean task success alone. — [arXiv:2401.08326](https://arxiv.org/pdf/2401.08326)
- **HammerBench** (arXiv:2412.16516) evaluates "fine-grained function-calling... in real mobile device scenarios," pushing benchmark realism toward actual deployed-agent contexts (mobile UI/OS tool use) rather than abstract APIs. — [arXiv:2412.16516](https://arxiv.org/pdf/2412.16516)
- A synthesizing 2026 survey, "The Evolution of Tool Use in LLM Agents: From Single-Tool Call to Multi-Tool Orchestration" (arXiv:2603.22862), explicitly periodizes the benchmark landscape: early benchmarks (**ToolAlpaca 2023, ToolBench 2023, BFCL v1 2024**) "focused on simple, one-step interactions with explicitly predefined parameters... relied on synthetic data and rule-based matching to measure... pass rates and structural accuracy"; later **BFCL v2/v3** "introduced multi-turn interactions, organizational tools, and multi-step logic, emphasizing continuous state management"; **NESTFUL (2024)** added call-dependency chains; **ComplexFuncBench (2025)** added implicit-parameter inference, user-defined constraint adherence, and long-context handling. It also notes that in **November 2024 Anthropic released the Model Context Protocol (MCP)** for tool↔harness standardization and in **2025 Google released an A2A protocol** for agent↔agent standardization — both reshaping what "realistic" tool-use evaluation now needs to cover. — [arXiv:2603.22862](https://arxiv.org/pdf/2603.22862)

### Inferences
- The "benchmark generation" arms race mirrors the underlying model-capability arms race: each new wave of benchmarks (v_n) is explicitly motivated as a fix for a known weakness of the v_(n-1) generation (single-turn → multi-turn; clean synthetic APIs → unstable real APIs; isolated calls → nested/dependent calls; abstract tasks → mobile/enterprise-realistic tasks). A workshop paper proposing a new optimization method should situate itself on this timeline and ideally report on at least one "modern" (multi-turn/nested/robustness) benchmark, not just BFCL v1-style AST matching, to be taken seriously against 2025–2026 reviewer expectations.
- No single benchmark dominates as the field's uncontested standard the way MMLU does for general LLM eval; BFCL (Berkeley) appears to be the closest thing to a continuously-maintained, versioned, community leaderboard standard, given its progression to v4 and its reproducible pinned-commit/PyPI-package evaluation harness.

## How is "accuracy" or "success" operationalized across these benchmarks?

### Takeaway
There is no single definition of "accuracy" in this literature — at least five distinct, non-interchangeable operationalizations are in active use: (1) exact/structural match on tool name + arguments (AST matching), (2) execution-based correctness (actually running the call and comparing output/state), (3) budgeted end-to-end task-completion rate ("pass rate"), (4) LLM-judge pairwise preference ("win rate"), and (5) decomposed per-capability scoring (planning/retrieval/calling separately, as in API-Bank and T-Eval). Papers must be read carefully to know which of these a reported "accuracy" number actually means.

### Cited Findings
- **AST (Abstract Syntax Tree) accuracy** (BFCL v1+): "examines the structural correspondence between the abstract syntax tree of the model-generated output, the ground-truth reference, and the formal function specification," checking correct function identification, inclusion/accuracy of required parameters, and correctness of parameter types and values — this is a static, non-executing match, comparable to exact-match string/structure comparison rather than running code. — [gorilla.cs.berkeley.edu/leaderboard.html](https://gorilla.cs.berkeley.edu/leaderboard.html); secondary synthesis at [arXiv:2510.22898](https://arxiv.org/pdf/2510.22898)
- **Executable Function Accuracy (EFA)** (BFCL): "the fraction of tasks where model-generated function calls execute successfully and match expected outputs" — i.e., the call is actually run and its *runtime* output is compared to ground truth, which is a stricter/different test than AST matching (a call can be structurally "correct" yet fail at execution, or vice versa for semantically-equivalent-but-syntactically-different calls). — [arXiv:2510.22898](https://arxiv.org/pdf/2510.22898)
- **Pass Rate** (ToolEval/ToolBench): defined precisely as "the proportion of successfully completing an instruction within limited OpenAI API calls" — this is a *budgeted, end-to-end task-success rate* (not per-call correctness): a trajectory of possibly many tool calls counts as one pass/fail unit, within an allowed call budget. — [ToolEval leaderboard](https://openbmb.github.io/ToolBench/); [arXiv:2307.16789](https://arxiv.org/abs/2307.16789)
- **Win Rate** (ToolEval/ToolBench): a *pairwise LLM-judge preference* metric, not an absolute accuracy — ChatGPT compares two full solution trajectories against criteria written as prompts and reports the percentage of comparisons favoring one method; validated at 80.3% agreement with human judges (vs. 87.1% agreement for pass rate judgments). — [ToolEval leaderboard](https://openbmb.github.io/ToolBench/)
- **Decomposed/sub-capability scoring** (T-Eval): rather than one "accuracy" number, T-Eval reports separate scores for instruction following, planning, reasoning, retrieval, understanding, and review, arguing this is "consistent with the outcome-oriented evaluation" while being more diagnostically granular. — [arXiv:2312.14033](https://arxiv.org/abs/2312.14033)
- **Capability-split accuracy** (API-Bank): accuracy/performance is reported separately across "planning, retrieving, and calling" rather than one merged score, enabling claims like "GPT-4 excels in planning" specifically (not tool-calling generally). — [arXiv:2304.08244](https://arxiv.org/abs/2304.08244)
- **Relevance/irrelevance detection** (implied by BFCL category structure and MetaTool's "tool usage awareness" task): some benchmarks score whether a model correctly *abstains* from calling any tool when none is appropriate, or correctly detects that the available tool set does not match the query — a form of accuracy oriented around false-positive tool invocation rather than argument correctness. — [gorilla.cs.berkeley.edu/leaderboard.html](https://gorilla.cs.berkeley.edu/leaderboard.html); [arXiv:2310.03128](https://arxiv.org/abs/2310.03128)
- **Multi-turn logical coherence / per-turn correctness** (BFCL v3): in multi-turn settings, accuracy is further split into whether each individual turn's call is correct (per-turn correctness) versus whether the whole dialogue state is tracked coherently across turns (multi-turn logical coherence) — these can diverge if a model gets individual calls right but loses track of accumulated state. — [arXiv:2510.22898](https://arxiv.org/pdf/2510.22898)
- Even "pass@k"-style sampling-based metrics (standard in code-generation evaluation) are referenced in the broader tool-use/agent literature as a way to report success probability over k sampled trajectories, though none of the core tool-calling benchmarks surveyed here (BFCL, ToolEval, T-Eval, API-Bank, MetaTool) was found to report pass@k as a headline metric in the sources retrieved — most instead use single-sample deterministic/greedy pass rate or AST/EFA matching. — *(inference; flagged — not independently confirmed per-benchmark in this pass, see Gaps)*

### Inferences
- "Accuracy" claims across this literature are not commensurable between papers: a BFCL "overall accuracy" (unweighted average of AST + executable categories) measures something structurally different from a ToolEval "pass rate" (budgeted end-to-end task completion) or a "win rate" (relative preference). A workshop paper comparing optimization methods against multiple benchmarks must report which specific metric family it is using per benchmark, and should avoid the common hand-wave of reporting a single unqualified "accuracy %" across heterogeneous benchmarks.
- The shift from static AST matching (v1-era) toward execution-based (EFA) and LLM-judge-based (win rate) metrics reflects an industry recognition that syntactic correctness is necessary but not sufficient for real-world tool-use success — this is directly relevant to motivating why "tool-use optimization" research should target execution-grounded or task-completion metrics rather than purely argument-matching metrics.

### Gaps
- Could not confirm whether any of the core surveyed benchmarks (BFCL, ToolBench/ToolEval, API-Bank, T-Eval, MetaTool, Seal-Tools) formally reports **pass@k** as a named metric with a precise definition (k independent samples, success if ≥1 succeeds) — this is common in code-gen benchmarks (e.g., HumanEval) but its explicit adoption in the tool-calling benchmark literature was not directly verified from primary sources in this research pass; flagged above as an unconfirmed inference rather than a stated fact.

## What known weaknesses or criticisms exist of these benchmarks?

### Takeaway
The dominant 2024–2026 criticisms are: (1) contamination (benchmark Q/A pairs leaking into pretraining or being retrievable via web search), (2) measurement artifacts caused by the model-serving/harness interface rather than the model itself, (3) unrealistic task simplicity (single-turn, single-tool, overly clean simulated environments where models behave "unrealistically flawless"), and (4) insufficient coverage of multi-turn, multi-tool, and dependent/nested call chains in the earlier benchmark generation — all of which has directly motivated a new wave of "fix" benchmarks (StableToolBench, FuncBenchGen, ToolRobustBench, ComplexFuncBench, NESTFUL, HammerBench).

### Cited Findings
- **Contamination**: "Existing benchmarks are vulnerable to data contamination from pretraining overlap and test-time web search, as benchmark question-answer pairs may be publicly accessible." This motivated **FuncBenchGen** (arXiv:2509.26553, "Towards Reliable Benchmarking: A Contamination Free, Controllable Evaluation Framework for Multi-step LLM Function Calling"), which generates *synthetic* multi-step tool-use tasks specifically to avoid this leakage risk. — [arXiv:2509.26553](https://arxiv.org/pdf/2509.26553)
- **Interface/harness-induced measurement artifacts**: "The observed tool-call rate is not a property of the model alone; it is a property of the model–interface stack that measures it" — i.e., different serving/evaluation harnesses can produce different apparent tool-use rates for the *same* model, which undermines cross-paper comparability. Source paper is explicitly about "Interface-Induced Trajectory Censoring," arguing a mismatched serving interface "distorts both what a benchmark measures and what RL training ever sees." — [arXiv:2609.03966](https://arxiv.org/html/2609.03966v1)
- **Unrealistic simulated environments**: "Existing benchmarks are overly idealized and neglect the complexity of multi-turn, multi-step settings in real-world scenarios," and "LLMs tend to behave in an unrealistically flawless manner when used in simulations, making tasks too easy to solve." — found in search synthesis around [arXiv:2604.06185 "Benchmarking LLM Tool-Use in the Wild"](https://arxiv.org/html/2604.06185)
- **Single-turn insufficiency**: "Single-turn benchmarks struggle to capture the diversity of real-world user interactions and fail to fully assess function-calling capabilities," and more pointedly: "single-turn tool dispatch is a necessary but not sufficient condition for agent viability" — i.e., passing a single-call benchmark does not establish that a model can function as a real multi-turn tool-using agent. This directly explains why BFCL moved from v1 (single-turn) to v3 (multi-turn, state-tracked) and why ComplexFuncBench, NESTFUL, and Seal-Tools all specifically target nested/dependent/multi-tool chains as a distinguishing design feature. — synthesis from search results around contamination/single-turn criticism queries; corroborated by [arXiv:2603.22862](https://arxiv.org/pdf/2603.22862) periodization of "simple, one-step interactions" as the earliest (now-criticized) benchmark generation
- **Instability of real-API-based evaluation**: StableToolBench's own stated motivation is that ToolBench-style benchmarking against *live* third-party APIs suffers "non-stationary API behavior over time (e.g., endpoints going offline, quota limits, or response-format drift)" plus "randomness in the evaluation process" — meaning raw ToolBench scores are not strictly reproducible over time, a significant and under-discussed threat to validity for any benchmark relying on calling real external services. — [arXiv:2403.07714](https://arxiv.org/abs/2403.07714)
- **Robustness gaps under perturbation**: RoTBench is built specifically because clean benchmark conditions don't reveal how much tool-calling accuracy degrades "under noisy conditions," implying standard benchmarks may overstate real-world reliability by testing only clean/canonical inputs. — [arXiv:2401.08326](https://arxiv.org/pdf/2401.08326); reinforced by 2026 **ToolRobustBench** ("Stage-Wise Perturbation Evaluation and Failure Diagnosis for Tool-Calling Agents," arXiv:2608.23635). — [arXiv:2608.23635](https://arxiv.org/pdf/2608.23635)
- **Constraint/structured-output trade-offs as a measurement confound**: the 2026 "Constraint Tax" paper shows that forcing strict structured-output constraints can itself suppress correct tool-calling behavior in open-weight models — meaning a benchmark's enforcement mechanism (e.g., requiring strict JSON schema conformance at decode time) can *artificially lower* measured tool-use accuracy independent of the model's "true" tool-use competence, confounding model-vs-model comparisons across differently-constrained evaluation setups. — [arXiv:2606.25605](https://arxiv.org/pdf/2606.25605)
- **Tool-selection/awareness gap persists even on "solved" benchmarks**: MetaTool's finding that "the majority of [8 popular LLMs] still struggle to effectively select tools" even in 2023/2024 highlights that strong AST/pass-rate numbers on execution-oriented benchmarks (BFCL, ToolEval) do not necessarily imply the more basic competency of knowing *whether and which* tool to use — an under-tested dimension relative to argument-generation accuracy. — [arXiv:2310.03128](https://arxiv.org/abs/2310.03128)

### Inferences
- The criticisms form a coherent through-line: early benchmarks optimized for easy-to-automate, structurally-checkable correctness (AST matching on synthetic single-turn tasks), which is now understood to (a) be gameable/contaminated, (b) not reflect real deployed-agent conditions (noisy, multi-turn, real unstable APIs, harness-dependent), and (c) not fully capture upstream decision-making (whether to use a tool at all). This strongly suggests a workshop paper on tool-use *optimization* should explicitly (i) disclose which benchmark generation (v1-style static vs. v3+-style multi-turn/robustness) it evaluates on, (ii) consider contamination risk if using any benchmark built before the authors' own model's pretraining cutoff, and (iii) report results under at least one perturbation/robustness or multi-turn condition to preempt the most common 2025–2026 reviewer criticism in this space.
- The "interface-induced" critique (arXiv:2609.03966) is particularly important for optimization papers specifically, since it implies that reported gains from a new "optimization" technique could be partially or wholly an artifact of how the technique's harness/serving stack measures tool calls, rather than a genuine capability improvement — this is a serious methodological trap that the target paper should explicitly guard against (e.g., by holding the harness constant across baseline and treatment).

### Gaps
- Did not find a dedicated, single "criticism/limitations" survey paper that comprehensively catalogs weaknesses across *all* the named benchmarks (ToolBench, API-Bank, BFCL, NexusRaven, StableToolBench, T-Eval, MetaTool, AgentBench, Seal-Tools) in one place; the criticisms above are assembled from several distinct 2025–2026 papers each addressing a subset of the problem, not from one authoritative source — a future search specifically for a "benchmark survey" or "evaluation pitfalls" paper (e.g., possibly within arXiv:2507.21504 "Evaluation and Benchmarking of LLM Agents: A Survey" or arXiv:2503.16416 "A Survey on Evaluation of LLM-based Agents," both found but not fetched in full) would likely consolidate this further.
- Did not independently verify quantitative evidence of contamination (e.g., a measured performance drop when a model is tested on a decontaminated/paraphrased version of a benchmark) beyond the qualitative claim in arXiv:2509.26553; no specific percentage-point contamination effect size was located.
