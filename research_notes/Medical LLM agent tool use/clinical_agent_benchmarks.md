# Medical/Clinical LLM Agent Tool-Use Benchmarks and Frameworks

## What are the major medical/clinical agent benchmarks that involve tool use, what tasks do they test, and what tools do agents access?

### Takeaway
There is now a dense ecosystem of clinical agent benchmarks spanning (a) simulated doctor-patient consultation with diagnostic-tool ordering (AgentClinic, AI Hospital, ClinicalLab), (b) realistic EHR/FHIR action benchmarks (MedAgentBench, FHIR-AgentBench), (c) multi-agent-vs-single-agent-vs-conventional-ML comparisons (MedAgentBoard), (d) hard medical reasoning under agent frameworks (MedAgentsBench), (e) risk-calculator tool learning (AgentMD), (f) clinical-trial multi-agent reasoning (ClinicalAgent), and (g) primary-care constrained-action-space safety benchmarks (GPAgentBench-2K). Each targets a different slice of "tool use" — from ordering simulated labs/imaging, to calling real FHIR GET/POST endpoints, to selecting the correct one of thousands of clinical calculators.

### Cited Findings
- **AgentClinic** (Schmidgall et al., arXiv:2405.07960, May 2024, published in *npj Digital Medicine*/Nature 2026 version at nature.com/articles/s41746-026-02674-7) is a multimodal benchmark with four agent roles: a **doctor agent** (the LLM under test), a **patient agent** simulating realistic patient responses, a **measurement agent** that returns diagnostic test results, and a **moderator agent** that judges the final diagnosis. The doctor agent can order simulated exams (temperature, blood pressure, EKG) and medical image readings (MRI, X-ray) through dialogue with the measurement agent, and also has access to tools such as a persistent **notebook tool**, adaptive retrieval, and reflection/experiential-learning cycles. It covers nine medical specialties and seven languages. — [AgentClinic project page](https://agentclinic.github.io/); [arXiv:2405.07960](https://arxiv.org/abs/2405.07960); [Nature npj Digital Medicine](https://www.nature.com/articles/s41746-026-02674-7)
- In AgentClinic's sequential decision-making format, diagnostic accuracy "can drop to below a tenth of the original accuracy" compared to solving the same questions as static MedQA problems, showing that interactive tool-mediated diagnosis is far harder than static QA. Claude-3.5 Sonnet achieved the highest diagnostic accuracy among tested LLMs, comparable to human physicians. Llama-3 showed up to a **92% relative improvement** when given the persistent notebook tool. — [arXiv:2405.07960](https://arxiv.org/abs/2405.07960)
- **MedAgentBench** (arXiv:2501.14654, Jan 2025; Stanford ML Group; also published as MedAgentBench v2 at PSB 2026 and in *NEJM AI*) is a FHIR-compliant virtual EHR environment with **300 patient-specific clinically derived tasks across 10 categories** written by human physicians, using realistic profiles of 100 patients with over 700,000 data elements. Tasks are split into "query-based" (information retrieval via GET requests) and "action-based" (medical record modification via POST requests). The agent orchestrator exposes ~9 FHIR-style functions: GET tools `condition.search`, `lab.search`, `vital.search`, `medicationrequest.search`, `procedure.search`, `patient.search`, and POST tools `vital.create`, `medicationrequest.create`, `procedure.create`, with a maximum of 8 interaction rounds per task. — [arXiv:2501.14654](https://arxiv.org/pdf/2501.14654); [Stanford ML Group project page](https://stanfordmlgroup.github.io/projects/medagentbench/); [MedAgentBench v2, PSB 2026](https://psb.stanford.edu/psb-online/proceedings/psb26/chen_eric.pdf); [NEJM AI](https://ai.nejm.org/doi/full/10.1056/AIdbp2500144)
- MedAgentBench uses **task success rate (pass@1)** as its main metric, justified by healthcare's "zero-tolerance error requirement," with manually curated reference solutions and rule-based sanity checks validating POST requests. Reported overall success rates: **Claude 3.5 Sonnet v2: 69.67%, GPT-4o: 64.00%, DeepSeek-V3: 62.67%, Gemini-1.5 Pro: 62.00%, Qwen2.5: 51.33%, Llama 3.3: 46.33%, Mistral v0.3: 4.00%.** Models consistently underperform on action-based (write) tasks relative to query-based (read) tasks. — [arXiv:2501.14654](https://arxiv.org/pdf/2501.14654)
- MedAgentBench v2 (PSB 2026, Eric Chen et al.) introduces prompt-engineering and tool-design improvements plus a memory component so the agent learns from prior failures, including new tools to format output correctly, to interact with the EHR without constructing raw HTTP requests (which were "prone to syntax errors"), and to perform math calculations. — [PSB 2026 paper](https://psb.stanford.edu/psb-online/proceedings/psb26/chen_eric.pdf); [ResearchGate summary](https://www.researchgate.net/publication/395098333_MedAgentBench_A_Virtual_EHR_Environment_to_Benchmark_Medical_LLM_Agents)
- **FHIR-AgentBench** (arXiv:2509.19319, Sept 2025) grounds 2,931 clinician-sourced questions in MIMIC-IV-FHIR data and systematically compares retrieval strategies (direct FHIR API calls vs. specialized retriever tools), interaction patterns (single- vs. multi-turn), and reasoning strategies (natural language vs. code generation). The best configuration (o4-mini, multi-turn + retriever + code generation) achieved only **0.5 answer correctness**; baseline configurations showed the highest rates of incorrect tool selection and incorrect FHIR resource-type selection, with "resource-type confusion and incorrect tool sequencing" identified as dominant failure modes in both retrieval and write tasks. — [arXiv:2509.19319](https://arxiv.org/pdf/2509.19319); [FHIR-AgentEval, PMC](https://pmc.ncbi.nlm.nih.gov/articles/PMC12919212/)
- **Agent Hospital** (arXiv:2405.02957, May 2024, Tsinghua) is a full-pipeline simulacrum where patient, nurse, and doctor roles are all LLM agents, modeling disease onset, triage, registration, consultation, exam, diagnosis, treatment, recovery, and follow-up. Doctor agents self-improve via a "Simulacrum-based Evolutionary Agent Learning" (SEAL) paradigm without manually labeled training data. After simulating treatment of roughly 10,000 patients (compressing >2 years of real-world practice), the evolved doctor agent reached **93.06% accuracy on a MedQA subset covering major respiratory diseases**, state-of-the-art versus other medical-agent methods on that MedQA subset. — [arXiv:2405.02957](https://arxiv.org/abs/2405.02957); [HuggingFace paper page](https://huggingface.co/papers/2405.02957)
- **MedAgentBoard** (arXiv:2505.12371, May 2025; NeurIPS 2025 Datasets & Benchmarks Track) systematically benchmarks multi-agent collaboration, single-LLM, and conventional (non-LLM) ML methods across four task categories: (1) medical (visual) QA, (2) lay summary generation, (3) structured EHR predictive modeling, and (4) clinical workflow automation — spanning text, medical images, and structured EHR data. Key finding: multi-agent collaboration helps task *completeness* in clinical workflow automation but does **not consistently outperform** advanced single LLMs on textual medical QA, nor specialized conventional ML methods on medical VQA and EHR-based prediction, which "generally maintain better performance." — [arXiv:2505.12371](https://arxiv.org/abs/2505.12371); [GitHub](https://github.com/yhzhu99/medagentboard)
- **MedAgentsBench** (arXiv:2503.07459, March 2025; published in *Patterns*; Gerstein Lab/Yale) constructs an 862-question "hard" subset drawn from eight established datasets (MedQA, PubMedQA, MedMCQA, MedBullets, MMLU, MMLU-Pro, MedExQA, MedXpertQA), selecting questions where fewer than 50% of tested models answer correctly, screened for contamination, and validated by four medical professionals on a five-level reasoning-depth rubric. GPT-4o drops from 88.2% accuracy on full MedQA to **32.2% on the hard subset**, showing agent/thinking frameworks are needed for genuinely complex reasoning; models like DeepSeek R1 and OpenAI o3 ("thinking models") significantly outperform standard prompting approaches on this hard subset. — [arXiv:2503.07459](https://arxiv.org/html/2503.07459v1); [GitHub](https://github.com/gersteinlab/medagents-benchmark)
- **AgentMD** (Jin, Chen, et al., arXiv:2402.13225, Feb 2024; published in *Nature Communications* 2025/2026, arXiv:2402.13225v / nature.com/articles/s41467-025-64430-x) is a "tool maker + tool user" language agent for clinical risk-calculator use. As tool-maker, it mines PubMed and curates **2,164 executable clinical calculators (RiskCalcs)** with >85% quality-check accuracy and >90% unit-test pass rate, screened from 33,033 candidate articles using GPT-3.5-Turbo. As tool-user, for a given patient note it retrieves the top-10 relevant calculators via MedCPT (a biomedical embedding model), then uses an LLM to select, compute, and summarize the applicable calculator(s). — [Nature Communications](https://www.nature.com/articles/s41467-025-64430-x); [arXiv:2402.13225](https://arxiv.org/abs/2402.13225); [NCBI PMC](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC12549800/)
- AgentMD "significantly outperforms GPT-4 for risk prediction (**87.7% vs. 40.9% accuracy**)" on held-out test cases, and on 698 real-world emergency-department notes it "accurately computes medical risks at an individual level." — [arXiv:2402.13225](https://arxiv.org/abs/2402.13225)
- **ClinicalAgent** (arXiv:2404.14777, April 2024; presented at ACM BCB '24) is a multi-agent system for **clinical-trial outcome prediction**, combining GPT-4, multi-agent architectures, and Med-PaLM with LEAST-TO-MOST and ReAct reasoning. It achieves **0.7908 PR-AUC** on clinical trial outcome prediction, a 0.3326 improvement over standard prompting, and is competitive with traditional ML models — notable because LLM/multi-agent systems "face challenges in clinical trial applications, primarily due to limited access to external knowledge." — [arXiv:2404.14777](https://arxiv.org/pdf/2404.14777)
- **GPAgentBench-2K** (arXiv:2608.30188, 2026; accepted EMNLP 2026) is framed as the first Constrained-MDP LLM-agent benchmark for primary-care decision-making, built from 2,428 de-identified real-world general-practitioner (GP) encounters. The agent (acting as a GP) chooses among six foundational clinical actions — **ask, body_exam, test, diagnose, treat, refer** — under a topological workflow prior and treats "refer" (safety-informed abstention) as a first-class outcome. Evaluating 16 state-of-the-art LLMs shows significant performance degradation as the action space scales, and a "clinical quality-safety gap": even frontier models with the highest diagnostic accuracy **violate safety constraints in over half of high-risk cases**. — [arXiv:2608.30188](https://arxiv.org/abs/2608.30188); [Hugging Face dataset](https://huggingface.co/datasets/Frank-xd/GPAgentBench-2K)
- **AI Hospital** (arXiv:2402.09742, Feb 2024; published COLING 2025) is a multi-agent medical interaction simulator with Doctor (the evaluated agent), Patient, and Examiner NPC agents, scored via a "Multi-View Medical Evaluation" (MVME) benchmark on Chinese medical records. It evaluates: Patient-agent response relevance/honesty vs. the underlying medical record; Examiner-agent accuracy in understanding requested exams and returning correct results; and Doctor-agent diagnostic consistency with the dialogue, rated on a 3-level scale (significantly inconsistent / slightly inconsistent / mostly consistent). — [ACL Anthology, COLING 2025](https://aclanthology.org/2025.coling-main.680/); [arXiv:2402.09742](https://arxiv.org/pdf/2402.09742)
- **ClinicalLab** is described (secondary source, via the medical-agents survey below) as a multi-department diagnostic benchmark covering **150 diseases across 24 medical specialties**. — [survey arXiv:2502.11211](https://arxiv.org/html/2502.11211) (secondary mention; primary ClinicalLab paper not independently verified in this pass — flagged as a gap)
- **MedAgentBench v2 / "A Survey of LLM-based Agents in Medicine: How far are we from Baymax?"** (arXiv:2502.11211, Feb 2025) catalogs additional workflow-simulation benchmarks: **MedChain (12,163 cases)**, AI Hospital, AgentClinic, and ClinicalLab, plus automated-evaluation frameworks **AI-SCE** and **RJUA-SPs**. — [arXiv:2502.11211](https://arxiv.org/html/2502.11211)
- **MDAgents** (arXiv:2404.15155, April 2024; NeurIPS 2024; MIT/Google Research/Seoul National University Hospital) is an *adaptive* multi-agent framework (not purely a benchmark but an architecture evaluated across benchmarks) that dynamically decides team structure — single clinician vs. multidisciplinary team — based on a four-stage pipeline: complexity assessment (low/moderate/high), expert recruitment, collaborative analysis, and final decision-making. It achieved best performance in **7 of 10 benchmarks** requiring medical knowledge and multimodal reasoning, with up to **11.8% improvement** over prior static multi-agent setups. — [arXiv:2404.15155](https://arxiv.org/abs/2404.15155); [GitHub](https://github.com/mitmedialab/MDAgents); [NeurIPS 2024](https://openreview.net/forum?id=EKdk4vxKO4)

### Inferences
- The field is bifurcating into two distinct benchmark families with different notions of "tool use": (1) *dialogue/diagnostic-tool-ordering* benchmarks (AgentClinic, AI Hospital, Agent Hospital) where "tools" are simulated exams/labs/imaging requested through natural-language dialogue with a measurement/examiner agent, and (2) *structured API/EHR-action* benchmarks (MedAgentBench, FHIR-AgentBench) where tools are literal function/API calls (FHIR GET/POST) much closer to general-domain tool-use benchmarks like BFCL. A workshop paper extending general tool-use-optimization work into healthcare should treat these as two different problem settings with different failure modes (dialogue-grounding/safety failures vs. schema/API-selection failures).
- MedAgentBoard's finding that multi-agent collaboration doesn't consistently beat single LLMs or conventional ML suggests that, at least as of mid-2025, "more agents" is not a free lunch in clinical tool-use/prediction tasks — directly relevant to an optimization-focused paper arguing for selective/adaptive multi-agent use (cf. MDAgents' complexity-adaptive approach, which did show gains).

## How is accuracy/success measured in these medical agent benchmarks?

### Takeaway
Metrics cluster into five families: (1) **diagnostic accuracy vs. ground-truth/exam answer** (MedQA/USMLE-style, used by AgentClinic, Agent Hospital, MedAgentsBench), (2) **task/tool-call success rate (often pass@1)** for structured EHR actions (MedAgentBench, FHIR-AgentBench), (3) **consistency/agreement-style human or LLM-judge rating** on a graded scale (AI Hospital's 3-level diagnostic consistency; moderator-agent judging in AgentClinic), (4) **predictive-task metrics** like PR-AUC/accuracy for risk or trial-outcome prediction (ClinicalAgent, AgentMD, MedAgentBoard's EHR prediction task), and (5) emerging **safety-adjusted / constraint-violation scoring** that discounts accuracy by unsafe actions (GPAgentBench-2K).

### Cited Findings
- AgentClinic uses a **moderator agent** to evaluate the doctor agent's final diagnosis against ground truth, reporting diagnostic accuracy; it additionally conducts **clinical reader studies** (human clinicians performing the same tasks for comparison) and tests robustness via **agent-injected biases** and perturbations, plus "patient-centric metrics" unique to the interactive setting. — [arXiv:2405.07960](https://arxiv.org/abs/2405.07960)
- MedAgentBench explicitly adopts **task success rate / pass@1** rather than partial credit, justified by stating healthcare's "zero-tolerance error requirement" — i.e., a clinical action is either fully correct (right resource, right values, right format) or counted as a failure, with rule-based sanity checks for POST (write) actions against manually curated reference solutions. — [arXiv:2501.14654](https://arxiv.org/pdf/2501.14654)
- FHIR-AgentBench reports **answer correctness** as its headline score (best configuration: 0.5) and separately logs categorical failure types — incorrect tool selection, incorrect FHIR resource type, incorrect tool sequencing — effectively a tool-selection-accuracy breakdown alongside end-task accuracy. — [arXiv:2509.19319](https://arxiv.org/pdf/2509.19319)
- MedAgentsBench measures plain **answer accuracy** against multiple-choice ground truth across standard medical QA datasets (MedQA, MMLU, etc.), but constructs a difficulty-filtered "hard" subset (questions <50% of models get right) specifically to make the metric discriminate between agent/reasoning frameworks rather than saturate. — [arXiv:2503.07459](https://arxiv.org/html/2503.07459v1)
- AI Hospital's Doctor-agent metric is not binary accuracy but a **3-level graded consistency rating** (significantly inconsistent / slightly inconsistent / mostly consistent) between the final diagnostic report and the full dialogue — an explicit acknowledgment that free-form diagnostic dialogue doesn't map cleanly onto single-answer accuracy. Patient-agent and Examiner-agent sub-scores (response relevance/honesty; exam-result-return accuracy) are evaluated separately, suggesting component-level ("tool"/NPC-level) evaluation rather than only end-to-end scoring. — [ACL Anthology COLING 2025](https://aclanthology.org/2025.coling-main.680/)
- GPAgentBench-2K implements explicit **safety-adjusted scoring**: it tracks safety-constraint violations alongside task/diagnostic accuracy so that a model cannot "win" by being accurate but unsafe; its headline finding is that frontier models with top diagnostic accuracy still violate safety constraints in **>50% of high-risk cases**, demonstrating a measurable "quality-safety gap" distinct from raw accuracy. — [arXiv:2608.30188](https://arxiv.org/abs/2608.30188)
- AgentMD and ClinicalAgent use standard **predictive-task metrics**: AgentMD reports classification accuracy for risk prediction (87.7% vs. GPT-4's 40.9%), and ClinicalAgent reports **PR-AUC (0.7908)** for clinical-trial outcome prediction. — [arXiv:2402.13225](https://arxiv.org/abs/2402.13225); [arXiv:2404.14777](https://arxiv.org/pdf/2404.14777)
- The medical-agents survey (arXiv:2502.11211) groups evaluation approaches into three categories across the field: **exact match** (accuracy/precision/recall for fixed-answer tasks), **semantic similarity** (BLEU, ROUGE, BERTScore for free-text generation), and **LLM-based/automated metrics** (e.g., ChatCoach-style LLM judges scoring coherence, relevance, reasoning quality, clinical-pathway alignment) — with human expert evaluation still considered necessary to validate diagnostic accuracy and safety. — [arXiv:2502.11211](https://arxiv.org/html/2502.11211)
- Agent Hospital reports outcomes in **USMLE-exam-style accuracy** terms: the evolved doctor agent reaches 93.06% accuracy on a MedQA (USMLE-derived) subset — i.e., tool-mediated simulated practice is evaluated by its downstream effect on a standard exam-style benchmark, rather than a bespoke interaction metric. — [arXiv:2405.02957](https://arxiv.org/abs/2405.02957)

### Inferences
- There is no single standardized "tool-use success" metric across medical agent benchmarks the way BFCL standardizes function-call-matching for general domains; clinical benchmarks instead bolt tool-use evaluation onto whatever end-task metric that sub-field already used (QA accuracy, PR-AUC, graded consistency). This is a gap a workshop paper could explicitly call out: medical tool-use benchmarks largely lack a BFCL-style decomposed metric (e.g., exact function-name match, exact-parameter match) — FHIR-AgentBench and MedAgentBench v2's failure-mode logging are the closest analogues currently available.
- Safety-adjusted scoring (GPAgentBench-2K) appears to be a 2026-era innovation not present in 2024 benchmarks (AgentClinic, Agent Hospital, AI Hospital), suggesting a temporal trend toward explicitly decoupling "accurate" from "safe" as the field matures — relevant framing for a paper on tool-use *optimization*, since optimizing purely for task accuracy could be shown empirically to increase unsafe tool invocations.

### Gaps
- Did not find a benchmark that reports **clinician inter-rater agreement (e.g., Cohen's kappa) between the agent's tool-selection/diagnosis and a panel of human clinicians** as a primary metric — several papers mention "clinical reader studies" or human validation (AgentClinic) but specific agreement statistics were not surfaced in the sources retrieved here.

## What specific tool types appear in clinical agent systems?

### Takeaway
Across the surveyed systems, six broad tool categories recur: (1) EHR/FHIR query-and-write tools (patient/lab/vital/medication/procedure/condition search and create endpoints), (2) clinical risk calculators (thousands of named scores, e.g., via AgentMD's RiskCalcs library), (3) drug-interaction/formulary lookup tools grounded in structured sources like RxNorm/DailyMed, (4) simulated diagnostic/measurement tools (vitals, EKG, imaging orders) mediated by a "measurement" or "examiner" agent, (5) medical literature/guideline RAG retrieval, and (6) code-execution/Python-interpreter tools for computation within clinical reasoning chains.

### Cited Findings
- **EHR/FHIR tools**: MedAgentBench's 9 concrete tools are `condition.search`, `lab.search`, `vital.search`, `medicationrequest.search`, `procedure.search`, `patient.search` (GET/read) and `vital.create`, `medicationrequest.create`, `procedure.create` (POST/write). — [arXiv:2501.14654](https://arxiv.org/pdf/2501.14654)
- FHIR-AgentBench's agents are additionally equipped with a **retriever tool** for loading FHIR resources and compare **direct API calls vs. a specialized retriever tool**, plus natural-language vs. code-generation reasoning modes. — [arXiv:2509.19319](https://arxiv.org/pdf/2509.19319)
- The RL-for-FHIR paper (Knorr, Müller, Bremer, Schweingruber, arXiv:2605.14126) frames the agent with exactly **two tools**: a retrieval tool to load clinical FHIR resources, and a **Python interpreter** for code execution within an "act–observe–think" loop, with an LLM-judge grading the final answer against FHIR-AgentBench ground truth to produce an RL reward signal. — [arXiv:2605.14126](https://arxiv.org/html/2605.14126)
- **Clinical calculators**: AgentMD's RiskCalcs library contains 2,164 executable calculators (e.g., risk/severity scores) curated from PubMed literature; tool *use* proceeds via retrieval of the top-10 relevant calculators with MedCPT embeddings, followed by LLM-based eligible-tool selection, computation, and summarization. — [arXiv:2402.13225](https://arxiv.org/abs/2402.13225) — Note: the key question's example calculators (MELD, CHA2DS2-VASc specifically) were not individually confirmed as named examples in the retrieved AgentMD sources; this is an inference that such widely-used named scores would fall within its general risk-calculator category, not a directly verified fact.
- **Simulated diagnostic/measurement tools**: AgentClinic's doctor agent orders simulated vitals (temperature, blood pressure, EKG) and image readings (MRI, X-ray) by querying a dedicated **measurement agent** rather than calling an API directly — i.e., "tool use" is dialogue-mediated rather than function-call-mediated. — [arXiv:2405.07960](https://arxiv.org/abs/2405.07960)
- AI Hospital's **Examiner agent** plays an analogous role — understanding a requested exam and returning the corresponding result — again as a simulated-tool-via-dialogue pattern rather than an API schema. — [ACL Anthology COLING 2025](https://aclanthology.org/2025.coling-main.680/)
- **Drug-interaction/formulary lookup**: a RAG-based drug-drug-interaction decision-support design integrates structured **RxNorm API lookups** with retrieval-augmented generation over **DailyMed structured product labels** (via ChromaDB), explicitly designed so interaction/severity claims are bounded by official documentation rather than generated freely by the LLM, because "general-purpose LLMs are unreliable for drug-drug interactions... can hallucinate severity, invent interactions, or fail to state the source of their claims." — [GitHub: rag-drug-interaction-decision-support](https://github.com/harshaps2119/rag-drug-interaction-decision-support) (Note: this is a GitHub project description rather than a peer-reviewed paper — treat as secondary/illustrative, not a benchmark result.)
- **Medical literature/guideline RAG**: the medical-agents survey (arXiv:2502.11211) describes agents incorporating "medical knowledge graphs, drug interaction databases, and clinical guideline repositories" to verify inferences against trusted sources, and other sources describe agents querying PubMed, Orphanet, and OMIM via RAG for knowledge retrieval. — [arXiv:2502.11211](https://arxiv.org/html/2502.11211)
- A guideline-grounded RAG system for ophthalmic clinical decision support (arXiv:2603.21925) is a domain example of literature/guideline retrieval tools feeding clinical decision support, reinforcing that "tying input information back to domain guidelines" is treated as a hallucination-mitigation design principle rather than only a performance hack. — [arXiv:2603.21925](https://arxiv.org/pdf/2603.21925)
- The medical-agents survey's taxonomy explicitly lists **"medical calculators, electronic health record interfaces, and image analysis software"** as the specialized-tool category, plus OCR for converting scanned documents to text and multimodal models for image analysis — covering imaging-report-style tools. — [arXiv:2502.11211](https://arxiv.org/html/2502.11211)

### Inferences
- Clinical tool ecosystems split into "hard" structured tools (FHIR APIs, RxNorm, calculators — deterministic, schema-constrained, closer to general-domain function calling) and "soft" simulated/dialogue tools (measurement/examiner agents in AgentClinic/AI Hospital — natural-language-mediated, not schema-constrained). A workshop paper on tool-use optimization should probably treat these as requiring different optimization strategies: schema-constrained tools benefit from BFCL-style function-calling optimization (parameter accuracy, tool selection), while dialogue-mediated simulated tools are closer to a sub-dialogue-generation problem.
- No benchmark was found that gives agents simultaneous access to *all* six tool categories in one integrated environment (e.g., EHR query + drug interaction + calculator + imaging + guideline RAG together) — each benchmark appears to specialize in one or two tool types. This fragmentation itself could be a point the workshop paper makes: general-domain tool-use benchmarks (ToolBench, BFCL) test broad multi-tool libraries, while medical benchmarks are tool-category-siloed, which may be why direct difficulty comparisons are hard (see next section).

### Gaps
- Could not directly verify named usage of specific clinical calculators like **MELD** or **CHA2DS2-VASc** inside any specific benchmark paper's text in this research pass (only the general "2,164 calculators" claim from AgentMD was verified) — flagged as not directly confirmed.
- Did not find a paper detailing a dedicated **imaging-report tool** (e.g., a radiology-report-generation or PACS-query tool) integrated into an agent *benchmark* specifically (as opposed to an agent architecture) — AgentClinic's "image reading" is ordered through the measurement agent but doesn't expose a separate imaging API tool per se.

## Are there published results on tool-use/tool-selection accuracy in medical benchmarks, and how do they compare to general-domain benchmarks (BFCL, ToolBench)?

### Takeaway
Medical tool-use benchmarks report substantially lower correctness than many general-domain function-calling leaderboards — e.g., FHIR-AgentBench's best configuration reaches only ~50% answer correctness and MedAgentBench's best model ~70% task success, versus BFCL v4's reported ~78.6% average accuracy across general tool-calling tasks — suggesting (with important caveats about non-comparable metrics) that clinical tool use, especially write/action tasks, is harder than typical general-domain tool calling. However, no paper was found that performs a *direct, controlled, apples-to-apples* comparison between a medical benchmark and BFCL/ToolBench using identical scoring methodology.

### Cited Findings
- **BFCL v4** (Berkeley Function-Calling Leaderboard): a recent validity audit found a **20.0% error rate** in the benchmark's own task construction, and an **18.5% misalignment rate** between its automated evaluator and human judgment on a 496-task expert-reviewed sample — i.e., even the general-domain reference benchmark has known reliability issues that complicate any cross-domain comparison. Reported overall BFCL v4 accuracy averaged **78.6%** across 14 models tested, varying significantly by task category. — [Benchmarking the Benchmarks: A Validity Audit of Tool-Calling Evaluation, arXiv:2607.02577](https://arxiv.org/html/2607.02577)
- On BFCL-v1, ToolACE-8B obtained **91.41% accuracy**, but accuracy on *mandatory* tool use remained **below 50% even for GPT-4o**, indicating that general-domain tool-use benchmarks themselves show wide variance depending on sub-task (optional vs. mandatory tool invocation). — [search result citing BFCL-v1/ToolACE figures] (secondary aggregation; original ToolACE paper not independently fetched in this pass)
- **FHIR-AgentBench** (clinical/EHR domain): best configuration (o4-mini, multi-turn + retriever + code) reached only **0.5 answer correctness**, with incorrect tool selection and incorrect FHIR resource-type selection as leading error categories — directly analogous to BFCL's "tool selection accuracy" concept but with a much lower top score than BFCL's ~78.6% average. — [arXiv:2509.19319](https://arxiv.org/pdf/2509.19319)
- **MedAgentBench** (clinical/EHR domain): best model (Claude 3.5 Sonnet v2) reached **69.67% task success**, with models showing a specific failure mode of outputting invalid/non-compliant action formats in **54% of cases** for some models, and notably weaker performance on action-based (write) vs. query-based (read) tasks — paralleling BFCL's general finding that "mandatory"/complex tool invocations are harder than simple ones. — [arXiv:2501.14654](https://arxiv.org/pdf/2501.14654)
- A Distill-Retrieve-Read framework applied to **medical QA with tool calling** showed tool-calling mechanisms enhance evidence-retrieval hit rates by **up to 30%** over non-distillation baselines in medication-consultation dialogs — evidence that tool-use mechanisms measurably help in medical retrieval tasks, though this is a lift/improvement number rather than an absolute accuracy figure comparable to BFCL. — [search result summary; original paper not independently fetched — treat as secondary]
- No source retrieved in this research pass performs a **direct, same-methodology comparison** explicitly stating "medical tool-use error rate is X% higher/lower than BFCL/ToolBench." The comparison above is an indirect juxtaposition of separately-reported top-line numbers (FHIR-AgentBench ~50%, MedAgentBench ~70%, BFCL v4 ~78.6% average) using different evaluation protocols (answer-correctness LLM-judge vs. pass@1 vs. categorical accuracy), so these numbers are **not strictly comparable** — a limitation the original papers' authors do not explicitly reconcile either.

### Inferences
- Within the EHR/FHIR tool-calling subdomain specifically, "write" (POST/action) tool calls are consistently harder than "read" (GET/query) tool calls (seen in both MedAgentBench and FHIR-AgentBench) — this mirrors a plausible general-domain pattern (state-changing actions being riskier/harder to get exactly right than information retrieval) but the medical benchmarks make this gap especially salient because wrong writes have direct patient-safety implications, which is likely why benchmarks like MedAgentBench adopted strict pass@1/zero-tolerance scoring rather than partial credit schemes more common in some general tool-use leaderboards.
- The absence of a BFCL-style decomposed tool-selection-accuracy metric as the *default* in most medical benchmarks (MedAgentBench and FHIR-AgentBench being partial exceptions) suggests an opportunity for a workshop paper: proposing a standardized, BFCL-style "medical function-calling accuracy" decomposition (tool-name match, parameter match, sequencing correctness) as a contribution, since currently only FHIR-AgentBench explicitly breaks down tool-selection vs. resource-type vs. sequencing errors.

## What frameworks/architectures are used for these medical tool-use agents (single-agent vs. multi-agent clinical teams)?

### Takeaway
The field spans a spectrum from single-agent-with-tools (MedAgentBench's orchestrator calling FHIR tools, AgentMD's tool-maker/tool-user agent) through sequential task-chain pipelines, to fixed-role multi-agent "clinical teams" (AI Hospital's Doctor/Patient/Examiner; Agent Hospital's Doctor/Nurse/Patient), to *adaptive* multi-agent frameworks that scale team complexity to case difficulty (MDAgents), with MedAgentBoard's empirical finding that fixed multi-agent setups do not reliably beat strong single agents.

### Cited Findings
- The medical-agents survey (arXiv:2502.11211) proposes **four architecture paradigms**: (1) **single agent** performing autonomous tasks end-to-end (e.g., clinical documentation); (2) **sequential task chain**, decomposing a workflow into stages (data ingestion → hypothesis generation → treatment planning → risk assessment) each with its own specialized tool; (3) **collaborative experts**, multiple specialized agents per clinical area (radiology, pathology, laboratory) communicating via standardized protocols to integrate findings; (4) **iterative evolution**, agents maintaining an experience base of past cases and self-refining over time (the paradigm behind Agent Hospital's SEAL). — [arXiv:2502.11211](https://arxiv.org/html/2502.11211)
- **MDAgents** (arXiv:2404.15155) is explicitly an *adaptive* multi-agent architecture: it assesses query complexity (low/moderate/high) and recruits either a single simulated clinician or a multidisciplinary team accordingly, mirroring how human clinical escalation works (primary-care physician vs. multidisciplinary tumor-board-style team). It beat static multi-agent baselines by up to 11.8% and won on 7/10 benchmarks tested. — [arXiv:2404.15155](https://arxiv.org/abs/2404.15155)
- **AI Hospital** and **Agent Hospital** both instantiate *fixed-role* multi-agent "clinical team" architectures (Doctor/Patient/Examiner; Doctor/Nurse/Patient respectively) as the simulation substrate itself, rather than as a technique layered onto a single benchmark task — i.e., the multi-agent structure *is* the benchmark environment. — [ACL Anthology COLING 2025](https://aclanthology.org/2025.coling-main.680/); [arXiv:2405.02957](https://arxiv.org/abs/2405.02957)
- **MedAgentBoard** empirically tested multi-agent collaboration against single-LLM and conventional-ML baselines and found multi-agent collaboration helps *task completeness* in clinical workflow automation specifically, but does **not consistently outperform** single strong LLMs (textual medical QA) or specialized conventional ML (medical VQA, EHR-based prediction) — an important counterpoint to assuming "more agents = better" in clinical tool-use tasks. — [arXiv:2505.12371](https://arxiv.org/abs/2505.12371)
- **AgentMD** is architected as a single agent with two distinct *roles* (tool-maker: curating calculators from literature; tool-user: retrieving/selecting/computing/summarizing for a given patient) rather than a multi-agent team — showing that "multi-role" and "multi-agent" are not synonymous in this literature. — [arXiv:2402.13225](https://arxiv.org/abs/2402.13225)
- The **RL-for-FHIR** paper (arXiv:2605.14126) uses a single **CodeAct-style agent** (act-observe-think loop with retrieval + Python-interpreter tools) post-trained with reinforcement learning using an LLM-judge reward — representative of a training-time optimization approach to single-agent clinical tool use, directly relevant to a "tool-use optimization" framing. — [arXiv:2605.14126](https://arxiv.org/html/2605.14126)
- **ClinicalAgent** uses a multi-agent architecture combining GPT-4-based and Med-PaLM-based agents with LEAST-TO-MOST decomposition and ReAct-style reasoning specifically for clinical-trial outcome prediction. — [arXiv:2404.14777](https://arxiv.org/pdf/2404.14777)
- **GPAgentBench-2K** evaluates LLMs acting as a *single* simulated GP agent operating under a constrained action space (ask/body_exam/test/diagnose/treat/refer) rather than a multi-agent team — representative of the "single-agent-with-constrained-tool/action-space" design pattern for safety-critical primary-care simulation. — [arXiv:2608.30188](https://arxiv.org/abs/2608.30188)

### Inferences
- There appears to be a real empirical tension in the literature: benchmark-simulation papers (AI Hospital, Agent Hospital, MDAgents) tend to showcase multi-agent/team architectures favorably, while a dedicated *benchmarking* paper designed to compare approaches head-to-head (MedAgentBoard) found multi-agent gains inconsistent outside workflow-completeness tasks. A workshop paper on tool-use optimization in healthcare could frame this as: "the benefit of multi-agent clinical teams is task-dependent and not yet reliably predictable, making adaptive-complexity approaches (MDAgents-style) or training-time tool-use optimization (RL-for-FHIR-style) more promising directions than fixed multi-agent role assignment."

### Gaps
- Did not find explicit computational-cost/latency comparisons between single-agent and multi-agent clinical architectures (relevant to any "optimization" framing beyond pure accuracy) in the sources gathered in this pass.
