# Optimizing When Agents Reach for Tools

LLM agent tool-use research has matured from "can a model call an API" to "should it, and at what cost" — yet the dominant finding across 2023–2026 literature is that **models remain poorly calibrated about whether to call a tool at all**, while the engineering community has discovered several large, nearly "free" efficiency wins (retrieval-based tool shortlisting, semantic caching, decoupled plan-then-execute architectures) that cut tokens, latency, and API calls by 3–100x with flat or improved accuracy. The clearest single finding — Kapoor et al.'s cost-controlled HumanEval comparison showing a trivial retry baseline (93.2% accuracy, $2.45) beating tree-search agent LATS (88%, $134.50) ([arXiv:2407.01502](https://arxiv.org/abs/2407.01502)) — establishes that "more deliberation" is not a reliable accuracy lever once cost is held constant, and that most published agent architectures have never been evaluated on a shared cost axis. At the same time, a convergent 2025–2026 body of work (When2Tool, "To Call or Not to Call," SMARTCAL) shows LLMs already encode an internal, linearly-decodable signal of tool necessity before generation, but systematically fail to act on it — meaning the dominant failure is a calibration gap, not a knowledge gap. Benchmarking itself remains fractured: at least five incompatible definitions of "accuracy" are in circulation (AST structural match, executable accuracy, budgeted pass rate, LLM-judge win rate, and decomposed per-capability scores), and the single most-cited leaderboard (BFCL) was found to contain defects in **48% of a sampled 50 questions** ([Epoch AI](https://epoch.ai/benchmarks/berkeley-function-calling-leaderboard/review)). This report synthesizes the foundations, selection/routing strategies, efficiency-accuracy techniques, orchestration frameworks, and failure modes that define the field, and closes with five concrete gaps suitable for seeding a workshop paper on choosing the optimal way to handle a task without sacrificing accuracy.

## Function calling matured into schema-constrained generation, but "accuracy" has no single definition

Tool/function calling in LLMs evolved through four layered approaches that still coexist in production systems today. **Toolformer** (Schick et al., Meta AI, Feb 2023) pioneered self-supervised learning of "which APIs to call, when to call them, what arguments to pass, and how to best incorporate the results," filtering candidate calls by whether they reduced the model's loss on subsequent tokens, using only a handful of demonstrations per API ([arXiv:2302.04761](https://arxiv.org/abs/2302.04761)). **ReAct** (Yao et al., Oct 2022) took a prompting-only path, interleaving reasoning traces with actions in a single text stream so "reasoning traces help the model induce, track, and update action plans" ([arXiv:2210.03629](https://arxiv.org/abs/2210.03629)). Fine-tuned specialist models followed — **Gorilla** (UC Berkeley/Microsoft, May 2023) trained LLaMA to write correct API calls and, with a document retriever attached, substantially reduced hallucinated API usage versus GPT-4 ([arXiv:2305.15334](https://arxiv.org/abs/2305.15334)); **ToolLLaMA/ToolBench** scaled this to 16,464 real RapidAPI endpoints and introduced **DFSDT** (Depth-First Search-based Decision Tree), a backtracking planner that generalizes ReAct's single linear chain into an explorable, prunable search tree ([arXiv:2307.16789](https://arxiv.org/abs/2307.16789)). The current default, however, is the **native provider function-calling API**: the developer passes a JSON-Schema `tools` parameter, the model returns a structured `tool_call` object rather than executing anything itself, and the calling application runs the function and feeds results back ([OpenAI docs](https://developers.openai.com/api/docs/guides/function-calling)). Underneath this sits **constrained/grammar-based decoding** — JSON Schemas compiled into finite-state machines so that at each decoding step, impermissible tokens are set to −∞ logit, making schema violations literally unsamplable (engines: Outlines, xgrammar, integrated into vLLM/SGLang) ([ZeroEntropy](https://zeroentropy.dev/concepts/constrained-decoding/)). This guarantee is not free: a 2026 study, "Constraint Tax in Open-Weight LLMs," documents that forcing strict JSON-schema decoding can *suppress* a model's willingness or ability to invoke tools correctly in open-weight models ([arXiv:2606.25605](https://arxiv.org/pdf/2606.25605)) — the first of several places in this literature where a fix for one failure mode visibly causes another.

Benchmarking this capability has no single standard. **BFCL** (Berkeley Function-Calling Leaderboard), now at v4, is the closest thing to a continuously-maintained standard, progressing from v1's AST (Abstract Syntax Tree) structural matching to v3's multi-turn, state-tracked evaluation and v4's "holistic agentic evaluation," and uniquely reports **Cost** and **Latency** alongside accuracy ([gorilla.cs.berkeley.edu/leaderboard.html](https://gorilla.cs.berkeley.edu/leaderboard.html)). But at least five non-interchangeable metrics compete across the field: **AST accuracy** (static structural match, no execution), **Executable Function Accuracy (EFA)** (the call is actually run and compared to ground truth), **Pass Rate** (ToolEval/ToolBench's budgeted end-to-end task-completion rate — one trajectory of possibly many calls counts as one unit), **Win Rate** (an LLM-judge pairwise preference score, validated at only 80.3% agreement with human judges versus 87.1% for pass rate) ([ToolEval leaderboard](https://openbmb.github.io/ToolBench/)), and **decomposed sub-capability scoring** (T-Eval splits "accuracy" into instruction-following, planning, reasoning, retrieval, understanding, and review, rather than reporting one number) ([arXiv:2312.14033](https://arxiv.org/abs/2312.14033)). This incommensurability is compounded by benchmark-quality problems: contamination (benchmark Q/A pairs leaking into pretraining, motivating the synthetic-task **FuncBenchGen**, [arXiv:2509.26553](https://arxiv.org/pdf/2509.26553)), non-stationary live APIs (motivating **StableToolBench**'s virtual API server and caching system, [arXiv:2403.07714](https://arxiv.org/abs/2403.07714)), and — most consequentially for any paper citing BFCL numbers — a direct audit finding **defects in 48% of 50 sampled BFCL questions** (20–70% by category), where correct, instruction-following responses could be marked wrong or incorrect responses marked correct ([Epoch AI](https://epoch.ai/benchmarks/berkeley-function-calling-leaderboard/review)). A separate measurement-validity concern, raised by the 2026 "interface-induced trajectory censoring" paper, is that "the observed tool-call rate is not a property of the model alone; it is a property of the model–interface stack that measures it" ([arXiv:2609.03966](https://arxiv.org/html/2609.03966v1)) — meaning any optimization paper must hold its serving harness constant between baseline and treatment or risk reporting an artifact as a capability gain.

## Retrieval and caching now do the routing work LLMs used to

As tool libraries scale from dozens to tens of thousands of entries, a two-stage pattern — cheap retrieval narrows the field, the LLM makes the final call among a short list — has become the field's default architecture, because it simultaneously controls token cost and avoids the accuracy collapse that comes from flooding context with irrelevant tool specs. The scale of the collapse is severe: on BFCL, accuracy for a calendar-scheduling task **dropped from 43% to 2%** as the tool set expanded from 4 to 51 tools, and tools placed in the *middle* of a prompt's tool list showed only 22–52% accuracy versus 31–32% for tools at the beginning or end — a "lost-in-the-middle" effect applied to tool lists ([TianPan.co](https://tianpan.co/blog/2026-04-19-over-tooled-agent-problem)). Separately, OpenAI's o3 accuracy fell from 98.1% to 64.1% as tool count grew, and once tool count exceeds roughly 30, "tool descriptions begin overlapping and the model struggles to choose correctly" (secondary synthesis, moderate confidence). Retrieval is the direct countermeasure: **Toollery** (2026), a training-free candidate-compression framework, improved Hit@1 from 0.553 to 0.920 on the SkillRouter benchmark (~79K capabilities) while cutting tokens from 43.1M to 27.7K, and on BFCL-V4 (457 tools) held AST accuracy at 0.837 versus 0.770 for full-library prompting while cutting input tokens from 84.1K to 2.1K and latency from 11.8s to 1.6s ([arXiv:2609.22218](https://arxiv.org/html/2609.22218v1)). Strikingly, ToolLLM's own retriever (searching the full 16,000+ API pool) achieved a **63.1% pass rate versus 60.0% for an oracle (hand-given, ground-truth) API set** — evidence that too many *correct* but unranked options can itself hurt reasoning, so a well-tuned retriever is an accuracy aid, not merely a cost filter (figures reported via secondary aggregator summary, flagged as approximate) ([arXiv:2307.16789](https://arxiv.org/pdf/2307.16789)). As libraries scale further, single-stage dense retrieval alone becomes insufficient — near-duplicate candidates and cross-family confusion emerge — motivating diversity-aware reranking: **Diverse Skill Routing (DSR)**, using Determinantal Point Processes, improved multi-skill-query Recall@20 from 0.704 to 0.739 on the ~80K-skill SkillRouter benchmark ([arXiv:2609.05824](https://arxiv.org/html/2609.05824v1)), and a chance-corrected adaptive-K method matched fixed top-50 performance with just **K≈7.4** candidates on BFCL (a 7x reduction), while on ToolBench a fixed K=5 "finds nothing on hard queries (correct tool ranked 6th–20th)" that adaptive K recovers 16.7% of ([arXiv:2605.24660](https://arxiv.org/html/2605.24660v1)).

A second, distinct routing literature concerns *who* decides, not just *what* is retrieved. Model-routing work (RouteLLM, GraphRouter, MasRouter) trains lightweight classifiers to send queries to a cheap versus expensive model, built on the design principle that "adding 500ms of LLM inference on top of 200–2,000ms model inference increases total latency by 25–250%" ([orq.ai](https://orq.ai/blog/llm-router)) — the same latency-compounding logic pushes tool-routing toward non-generative classifiers/rerankers rather than a full LLM "pre-flight" call. A notable gap: **no paper was found that benchmarks a standalone tool-router classifier (RouteLLM's analog for tools) head-to-head against both full-context listing and embedding retrieval with efficiency and accuracy in one table** — the literature currently treats this as either a retrieval problem or folds it into multi-agent delegation. Hierarchical delegation is the coarse-grained version of the same idea: a planner LLM assigns whole subtasks to specialist agents rather than picking individual tools, shrinking the action space the top-level planner must search ("Agent-as-Tool," [arXiv:2507.01489](https://arxiv.org/pdf/2507.01489); AgentOrchestra's Tool-Environment-Agent protocol, [arXiv:2506.12508](https://arxiv.org/html/2506.12508v4)). Comparative benchmarking of multi-agent frameworks (AutoGen's conversational dynamic delegation, MetaGPT's SOP-encoded role pipeline, CAMEL's inception-prompted role-play) shows large, task-dependent differences — in one code-generation task AutoGen produced an outline with 1 agent in 40 seconds, MetaGPT a full program with 6 agents in 580 seconds ([MegaAgent, ACL Findings 2025](https://aclanthology.org/2025.findings-acl.259.pdf), secondary synthesis) — but the dominant cost driver is not framework choice; it is delegation correctness, since "incorrect delegation by the manager agent" and "workers duplicating effort" are the named efficiency failure modes across the orchestration-pattern literature. A token breakdown from MetaGPT's own pipeline is telling: the task-solving (tool-execution) phase consumed roughly **20x the tokens of the planning phase** (1,153,595 vs. 55,294 total tokens), implying that cheap upfront investment in better planning/routing has outsized leverage over expensive downstream execution.

The single largest efficiency lever in this section, by reported magnitude, is **semantic caching of tool outputs**. Asteria (2025), a cross-region semantic cache built specifically for agentic tool access, is motivated by the finding that "external data retrieval consistently constitutes around 40–50% of total execution time," and that a 100M-user service making 10 tool calls per query could incur $150,000/day in API fees ([arXiv:2509.17360](https://arxiv.org/html/2509.17360v1)). Its two-stage design — an ANN index for candidate matching (similarity threshold 0.9) followed by a 1B-parameter "Semantic Judger" that validates true equivalence before confirming a cache hit — achieved **3.6–5.7x throughput gains, 85–95% cache hit rates (versus under 20% for exact-match caching), a 92% reduction in external API calls** (1,300→103 in one scenario), and 6x more throughput per dollar, with accuracy "virtually identical to non-cached baseline" ([arXiv:2509.17360](https://arxiv.org/html/2509.17360v1)). Crucially, the paper's own ablation shows *why* the validation stage is not optional overhead: removing it (ANN-only matching) measurably hurt accuracy, e.g., 0.69 versus 0.79 on StrategyQA — a concrete, reproducible instance of a caching mechanism silently corrupting correctness when similarity alone is trusted. Simpler exact-argument memoization matters too: one production anti-pattern logged **800 calls to a geocoding tool for only 40 unique addresses** (760 duplicates), fixable by hashing tool name plus normalized arguments ([jsmanifest.com](https://jsmanifest.com/claude-code-tool-result-caching-2026)). At a different grain, Voyager's "ever-growing skill library" reuses entire successful tool-use *programs* rather than individual call outputs; ablating it caused a **15.3x loss in tech-tree milestone speed** in Minecraft, suggesting experiential skill-reuse can dominate raw output caching as a performance driver (secondary synthesis of [arXiv:2305.16291](https://www.emergentmind.com/papers/2305.16291)). Across retrieval, routing, and caching alike, the recurring architectural primitive is the same: a cheap, approximate first pass followed by a stricter validation/reranking stage — and the single clearest place accuracy measurably degrades is precisely when that second stage is skipped.

## Calibrated gating and cost-aware stopping beat blanket prompting

The central 2025–2026 finding on *whether* to call a tool at all is that models already possess the relevant knowledge internally but fail to act on it — a calibration problem, not a knowledge problem. **When2Tool / Probe&Prefill** (May 2026) shows across an 18-environment benchmark that "tool necessity is linearly decodable from the pre-generation representation with AUROC 0.89–0.96," and their probe-plus-steering method "reduces tool calls by 48% with only 1.7% accuracy loss," versus the best training-free baseline's 6% reduction or "5x higher accuracy loss" at comparable reduction ([arXiv:2605.09252](https://arxiv.org/abs/2605.09252)). A companion paper, "To Call or Not to Call: A Framework to Assess and Optimize LLM Tool Calling," trains "Latent Need Estimators" from hidden states that predict genuine tool necessity more accurately than the model's own self-reports, documenting systematic misalignment between a model's perceived and actual tool-use value across six open models plus a proprietary OpenAI model ([arXiv:2605.00737](https://arxiv.org/abs/2605.00737)). A related paper on the "When2Call" benchmark quantifies the resulting asymmetry directly: six models across three families show "high call accuracy but much lower no-call accuracy, leaving overall accuracy in the 55–70% range" — models are far worse at correctly *refraining* from a call than at making a needed one ([arXiv:2605.18882](https://arxiv.org/abs/2605.18882)). Their proposed fix, Adaptive Margin-Calibrated Steering (AMCS), applies "a closed-form counter-bias shift along sparse-autoencoder decoder directions" to cancel this over-calling bias with "negligible drop in call accuracy." SMARTCAL, independently, finds overconfident tool misuse ("tool-abuse") is "a common issue regardless of model capability" across multiple SOTA LLMs, and its calibration approach yields an 8.6% average QA performance increase alongside a 21.6% decrease in Expected Calibration Error ([arXiv:2412.12151](https://arxiv.org/abs/2412.12151)). Because these interventions operate on hidden states rather than requiring additional generated reasoning tokens, they achieve efficiency gains at near-zero added inference cost — a materially better cost/accuracy regime than prompting-based suppression, which "reduces calls indiscriminately across all difficulty levels, including hard tasks where tools are genuinely needed," so that "hard tasks lose substantially more accuracy per saved call than easy tasks" (moderate-confidence, search-aggregated finding).

A parallel 2025–2026 literature makes cost *explicit* as a state variable the agent must track, rather than implicit in a prompt. "Budget-Aware Tool Use Enables Effective Agent Scaling" (Google Research et al., COLM 2026) shows that "simply granting agents a larger tool-call budget fails to improve performance" absent budget awareness; their **Budget Tracker** and **BATS** (Budget-Aware Test-time Scaling) methods "cut API costs by over 30% while boosting accuracy" and formally extend the cost-performance Pareto frontier versus budget-blind baselines ([arXiv:2511.17006](https://arxiv.org/abs/2511.17006)). **CostBench**, a benchmark of multi-turn travel-planning tasks with multiple cost-varying solution paths and dynamic disruptions (tool failures, cost changes), finds even the best tested model achieves **under 75% exact match** on cost-optimal plan selection on static tasks, and performance drops a further **~40%** under dynamic disruption ([arXiv:2511.02734](https://arxiv.org/abs/2511.02734)) — strong evidence that current benchmarks measuring cost-aware planning in static settings overstate real-world robustness. "Scores Are Not Decisions: Cost-Aware Stopping for Tool Acquisition" (CAM-DF) makes the complementary point that score-only ranking rules are suboptimal when tool costs are heterogeneous; on τ-bench Retail, its stopping policy "exposes the agent to 37% fewer tools than full access while maintaining comparable task success" ([arXiv:2607.27083](https://arxiv.org/abs/2607.27083)). Early-stopping research converges on the same idea from the loop-termination angle: **HALT** stops multi-hop search agents once accumulated evidence matches expected hop claims rather than using a fixed step count ([arXiv:2608.02009](https://arxiv.org/html/2608.02009)), and Semantic Early-Stopping grounds halting in per-round output-similarity rather than a blind counter ([arXiv:2606.27009](https://arxiv.org/pdf/2606.27009)) — though quantitative accuracy/efficiency deltas for these two specific papers were not independently retrieved and should be treated as directionally supportive rather than confirmed numbers. Taken together with CAM-DF's finding that "true utility gain plateaus as the number of calls increases," this body of work supports an inverted-U or saturating model of tool-call value: the first few genuinely necessary calls carry most of the task-success value, and additional calls beyond a small core contribute little marginal accuracy while adding cost — exactly the regime where calibrated gating and cost-aware stopping produce large efficiency wins (37–48% call reductions across independent papers) for ≤2% accuracy loss.

## Decoupled planning beats reasoning-heavy search once cost is controlled

Orchestration frameworks span a spectrum from single-pass/decoupled tool use to interleaved reasoning-acting to deliberative tree search, and the central empirical surprise is that accuracy does not reliably rise with more LLM calls spent per task. **ReWOO** (May 2023) decouples a Planner (produces a full blueprint before any tool call), Worker (executes calls), and Solver (synthesizes the final answer), avoiding ReAct's "reason → call → wait → re-reason on full prior context" loop; this shifts token cost from quadratic to linear in reasoning steps, delivering **5x token efficiency and a 4% accuracy improvement on HotpotQA** versus interleaved baselines ([arXiv:2305.18323](https://arxiv.org/abs/2305.18323)). **LLMCompiler** (Dec 2023, ICML 2024) generalizes this with an explicit DAG: a Function Calling Planner builds the task graph, a Task Fetching Unit dispatches ready tasks, and an Executor runs independent calls in parallel, reporting **up to 3.7x latency speedup, 6.7x cost reduction, and ~9% accuracy improvement versus ReAct**, plus 1.35x latency over OpenAI's native parallel function calling at similar accuracy ([arXiv:2312.04511](https://arxiv.org/abs/2312.04511)). Both papers report simultaneous accuracy *and* efficiency gains over sequential ReAct — directly contradicting the assumption that efficiency must trade off against accuracy, and suggesting that at least part of ReAct's accuracy cost comes from redundant, repeatedly-reprocessed context rather than from genuinely necessary deliberation. The caveat is that this "free lunch" is architecture-dependent: it requires tasks whose tool-call structure decomposes predictably upfront, and may not transfer to highly adaptive tasks where each result changes the next step's plan (consistent with CostBench's ~40% accuracy drop under dynamic disruption, above).

Deliberation-heavy methods tell the opposite story once cost is held constant. **Reflexion** (Shinn et al., 2023) adds verbal self-reflection in episodic memory across sequential trials, reporting 91% pass@1 on HumanEval versus GPT-4's then-baseline 80% ([arXiv:2303.11366](https://arxiv.org/abs/2303.11366)); **LATS** (Zhou et al., Oct 2023) unifies reasoning/acting/planning via MCTS-style tree search, reporting HumanEval pass@1 of 92.7% and a HotPotQA exact-match of 0.63 versus ReAct's 0.32 ([arXiv:2310.04406](https://arxiv.org/abs/2310.04406)) — but LATS requires "5–20x more LLM calls than simpler approaches like ReAct" ([agentic-patterns.com](https://www.agentic-patterns.com/patterns/language-agent-tree-search-lats/)). When Kapoor et al. ("AI Agents That Matter," Princeton, July 2024) re-ran these methods under a shared cost axis on HumanEval, the ranking inverted: **LATS reached 88% accuracy at $134.50; Reflexion reached 87.8% at $3.90; LDB reached 91% at $2.19; and a trivial "warming" baseline (gradually raising sampling temperature and retrying) reached 93.2% at $2.45** ([arXiv:2407.01502](https://arxiv.org/abs/2407.01502)). The paper's explicit conclusion — "state-of-the-art agent architectures for HumanEval do not outperform simple baselines" once cost is controlled — is arguably the single most load-bearing citation available for a workshop paper's motivation, and the authors additionally report finding implementation bugs in both LATS's and STeP's benchmark harnesses that marked incorrect solutions as correct, a direct methodological warning against trusting raw framework-vs-framework numbers. The same Pareto-frontier logic recurs on τ-bench, where agents are explicitly ranked by whether they sit on the accuracy-cost frontier (evaluation cost on the Airline benchmark ranged **$22–$180** across agents) ([HAL τ-bench](https://hal.cs.princeton.edu/agent/TAU-bench%20Tool%20Calling)), and on GAIA, where GPT-4o used ~1,380 tokens/task ($0.079 total) versus Gemini 2.5 Flash's ~5,300 tokens/task ($0.19 total) for comparable scores — illustrating that "a high GAIA score achieved with an enormous number of tool calls is a different product from the same score achieved cheaply" ([HF GAIA blog](https://huggingface.co/blog/hetline/lessons-learned-on-gaia-agents)). A notable and persistent gap: **no single paper runs ReAct, Toolformer, Reflexion, LATS, Plan-and-Solve, ReWOO, and LLMCompiler all on one shared benchmark with one shared base model**, reporting accuracy + tokens + latency + dollar cost for all seven — every comparison in this literature is reconstructed across papers with different benchmarks and models, which is itself a concrete contribution opportunity. Beyond frameworks, a general empirical study of diminishing returns, **Efficient Agents** (July 2025), explicitly investigates "when additional modules produce diminishing returns," reporting a proposed framework that retains 96.7% of a leading open-source agent's performance while cutting operational cost per task from $0.398 to $0.228 — a 28.4% improvement in "cost-of-pass," a combined cost-accuracy metric ([arXiv:2508.02694](https://arxiv.org/abs/2508.02694)). A layered pattern recurs across both rigorous and practitioner sources: route cheap/fast models or deterministic logic to tool selection and task decomposition, and spend expensive-model tokens only on final synthesis or genuinely hard sub-tasks — ReWOO's architecture explicitly enables distilling its Planner/Solver reasoning from 175B GPT-3.5 into a fine-tuned 7B LLaMA ([arXiv:2305.18323](https://arxiv.org/abs/2305.18323)), and Kapoor et al.'s own DSPy-based joint cost/accuracy optimization cut variable cost 53% (GPT-3.5) and 41% (Llama-3-70B) on HotPotQA while preserving accuracy ([arXiv:2407.01502](https://arxiv.org/abs/2407.01502)). Practitioner-reported savings for this "cheap router + expensive synthesizer" pattern range widely (40–90%) across non-peer-reviewed sources and should be read as directional consensus, not a settled, benchmarked number — no peer-reviewed paper was found that isolates this specific split as its own ablated variable.

## Failure modes cluster into selection, calling, and post-call stages

A 2026 taxonomy, **ToolFailBench**, formalizes the recurring failure categories into four tool-required types plus two control-task types: **Tool-Skip (TS)** (no valid executed call, including refusal), **Result-Ignore (RI)** (the correct tool is called and returns data, but the final answer doesn't faithfully reflect it — e.g., memorized values replacing tool data), **Output-Fabrication (OF)** (invented structured data presented plausibly), and **Unnecessary-Tool-Use (UTU)** (a tool is called when none was needed) ([arXiv:2607.04686](https://arxiv.org/html/2607.04686)). Quantitatively, even the best model tested (Grok-4.3) reached only an **86.33% Clean Tool-Use Rate**; some Llama-3.1 models show an "Always-Call" pattern with Unnecessary-Tool-Use Rate ≥77%; and the Finance domain shows the highest median Result-Ignore Rate (12.24%) versus Cybersecurity's 0.68% — evidence that failure rates are highly domain-dependent, not a single global property of a model ([arXiv:2607.04686](https://arxiv.org/html/2607.04686)). These failures map cleanly onto three pipeline stages: *selection-stage* failures (wrong tool among similar candidates, tool hallucination, context-bloat-induced misselection — e.g., the 43%→2% BFCL accuracy collapse as tool count rose from 4 to 51, discussed above); *calling-stage* failures (argument/parameter hallucination — "a model that has seen `delete_file` in a thousand traces will happily emit `wipe_disk`"); and *post-call* failures (Result-Ignore, Output-Fabrication, brittle error recovery). Tool hallucination itself splits into **Tool Selection Hallucinations** (non-existent or irrelevant tools chosen overconfidently) and **Tool Calling Hallucinations** (incorrect, omitted, or fabricated parameters) ([arXiv:2609.19425](https://arxiv.org/pdf/2609.19425)) — and a structural limit applies to mitigating the former: "a gate can only decide about a tool it placed in the visible set; a hallucinated tool is by definition not something a gate chose to expose," meaning selection-stage filtering cannot, by construction, catch hallucinations of tools outside the exposed set.

Mitigations map onto these same three stages, each with its own carried tradeoff. Pre-selection filtering (RAG-MCP/Tool RAG, adaptive-K) is reported to **triple tool-selection accuracy (13%→43%) while reducing prompt tokens by over 50%** ([Writer Engineering](https://writer.com/engineering/rag-mcp/)). Generation-time constraints (constrained decoding, strict schemas, closed-world prompting restricting the model to acknowledge only explicitly-provided tools) "eliminate malformed tool call arguments as a failure category" by construction — but closed-world resolution's own authors flag that "how the approach performs with large, dynamically expanding tool sets remains unclear" and that over-restriction risks "potential performance degradation" ([arXiv:2609.19425](https://arxiv.org/pdf/2609.19425)), while the Constraint Tax finding (above) shows the same generation-time fix can itself suppress tool-calling in open-weight models — a direct illustration that mitigations at this stage are not strictly additive. Post-call diagnosis and recovery is the least mature stage: differentiated recovery-action spaces ("Retry, Skip, Replan, Substitute_Tool, Escalate_Fidelity, Regenerate_Prior_Step, Escalate") show that "different failure classes benefit from different recovery actions, with retry being useful for transient failures but poorly matched to stale retrieval context, schema drift, contradictory evidence, or wrong-but-plausible semantic outputs" — i.e., naive blanket retry is an inadequate universal mitigation (moderate-confidence, search-synthesized finding). Newer internal-state probing work — "A Few Neurons Reveal When LLMs Misuse Tools" ([arXiv:2608.00218](https://arxiv.org/pdf/2608.00218)) and "The Calls are Coming from Inside the Model" ([arXiv:2608.27750](https://arxiv.org/pdf/2608.27750)) — proposes catching misuse from internal activations before or as it happens, rather than filtering outputs post-hoc, echoing the same hidden-state-probe pattern seen in Section 3's gating literature. No mitigation found directly targets "confidence calibration for the decision to call a tool at all" as a first-class, named technique distinct from error *detection* — the closest analogs (Probe&Prefill's tunable threshold, the internal-neuron probes) are detection-adjacent rather than pre-call calibration, which the research notes flag as a potential novel framing angle in its own right.

## Five gaps point to a genuine workshop contribution

Pulling the preceding sections together, the field has solid, well-evidenced techniques at each individual stage — retrieval for selection, constrained decoding for calling, caching for reuse, calibrated gating for whether-to-call, decoupled planning for parallelization — but lacks any unifying framework that jointly optimizes *which* stage to invest cost in for a given task, and lacks the shared benchmarking infrastructure to prove such a framework works. Five concrete directions emerge as novelty-bearing and currently open:

1. **A unified, cost-axis-controlled N-way framework comparison.** No paper runs ReAct, Toolformer, Reflexion, LATS, ReWOO, and LLMCompiler on one shared benchmark, one shared base model, reporting accuracy + tokens + latency + dollar cost together — every number in Section 4's table comes from a different paper's self-chosen benchmark. Kapoor et al.'s HumanEval table is the only rigorous precedent, and it covers just four of these eight methods ([arXiv:2407.01502](https://arxiv.org/abs/2407.01502)). Building this comparison — ideally paired with the Holistic Agent Leaderboard's (HAL) infrastructure ambitions ([arXiv:2510.11977](https://arxiv.org/pdf/2510.11977)) — would let a workshop paper make falsifiable Pareto-frontier claims rather than cross-paper analogies.

2. **A standalone tool-router classifier benchmarked against both full-context listing and embedding retrieval.** The model-routing literature (RouteLLM) has this comparison for *model* selection; the tool-routing literature does not have the analog for *tool* selection — it is currently folded into either retrieval papers or multi-agent delegation papers, never isolated as its own ablated variable with efficiency and accuracy reported together.

3. **A principled methodology for choosing K (how many tools to expose) as a function of task difficulty.** "How Many Tools Should an LLM Agent See?" states explicitly that "no standard methodology exists to tell the builder whether the chosen K was appropriate," and that existing benchmarks "were not designed to evaluate search depth" ([arXiv:2605.24660](https://arxiv.org/html/2605.24660v1)) — this is the single sharpest, most quantitatively actionable open-problem statement found anywhere in this research, sharper than the mostly qualitative gaps named in broad agent surveys.

4. **Pre-call confidence calibration as a first-class technique, distinct from post-hoc error detection.** The gating literature (Probe&Prefill, LNEs, AMCS, SMARTCAL) converges on fixing the misalignment between a model's latent "knows when a tool is needed" signal and its emitted behavior, but no paper names or benchmarks "tool-use confidence calibration" as its own technique category separate from internal-state *misuse detection* — the two are currently conflated, and a workshop paper could be the first to formalize the distinction with a dedicated calibration-error metric (analogous to Expected Calibration Error, as SMARTCAL gestures toward) applied specifically to the call/no-call decision.

5. **Robustness of cost-aware and stopping policies under dynamic, adversarial cost shifts.** CostBench shows a ~40% accuracy drop under dynamic disruption versus static conditions ([arXiv:2511.02734](https://arxiv.org/abs/2511.02734)), and every early-stopping/cost-aware-stopping paper surveyed (CAM-DF, HALT, Semantic Early-Stopping) was evaluated only in comparatively static settings. A workshop paper demonstrating a stopping/gating policy that degrades gracefully — rather than catastrophically — under live cost or tool-availability shocks would address a documented, unresolved stress test rather than compete on an already-crowded static-benchmark leaderboard.

## Conclusion

The field's trajectory suggests that "optimal tool use" is converging into a single underlying design pattern — a cheap, approximate first pass (retrieval, a trained classifier, a hidden-state probe) gated by a stricter second-stage validator (a reranker, a semantic judger, an executable check) — that recurs independently across tool selection, result caching, model routing, and now tool-necessity gating. The strongest counter-finding to keep front-of-mind is that this pattern is not a guaranteed safety net: every measured instance of a selection/caching/gating mechanism actually hurting accuracy in this research traces back to skipping that second validation stage (Asteria's ANN-only ablation, naive prompt-based call suppression, the Constraint Tax's suppression of legitimate calls). This reframes the workshop paper's central claim productively: the open question is not whether efficiency and accuracy trade off — the Kapoor et al. and LLMCompiler/ReWOO results show they frequently don't — but under what conditions a two-stage coarse-then-precise architecture holds, and what happens when its validator is cheap, missing, or itself miscalibrated. A contribution that formalizes *when* the validation stage can be safely skipped or cheapened — rather than proposing yet another retrieval or caching mechanism in isolation — would sit precisely at the field's current frontier, where the engineering techniques are individually mature but the theory connecting them to a single accuracy-preserving operating point does not yet exist.
