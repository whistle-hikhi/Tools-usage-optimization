# The medical tool-catalog ecosystem is a layered stack, not a single competitive field

ToolUniverse (Harvard, Zitnik Lab) is one node in a larger, fast-growing ecosystem of tool catalogs, data commons, and packaging formats that medical/biomedical LLM agents draw on — and the research notes behind this report (`research_notes/Medical AI agent tool catalogs/`) organize that ecosystem into five layers rather than one flat list. At the top sit **general-purpose "AI scientist" toolboxes** — ToolUniverse itself (600+/1000+ tools, dozens of prebuilt agent skills, MCP-compatible, powering the therapeutic-reasoning agent **TxAgent**) and its closest peer, Stanford's **Biomni** (150 tools, 105 software packages, 59 databases, mined from ~2,500 papers across 25 subfields, paired with a retrieval-augmented planner and a "Know-How Library" of protocols) ([ToolUniverse](https://github.com/mims-harvard/tooluniverse); [Biomni](https://github.com/snap-stanford/biomni)). Both solve the same underlying problem the companion report's general-domain literature already named as dominant — cheap retrieval narrows a large tool pool, then LLM reasoning makes the final selection — but neither is cited by any of the clinical-benchmark papers already covered in the companion medical report (MedAgentBench, FHIR-AgentBench, AgentClinic, AgentMD, MeNTi, EHR-MCP); they sit one layer below those benchmarks, as the substrate an agent could be *built from*, not an evaluation harness.

Beneath that sits a **calculator- and FHIR-specific tool layer** that the companion report already covers in research terms (AgentMD's 2,164-calculator RiskCalcs library retrieved via MedCPT, MeNTi's 281-tool nested-calling toolkit) but which has recently moved from bespoke research pipelines into standardized packaging: **medical-calc-mcp** ships 121 PMID-cited calculators as a plain MCP server usable by any Claude/GPT agent without reimplementing retrieval logic, and an analogous production layer exists for FHIR itself — **HealthChain** (a typed, validated FHIR SDK) and an open **MCP-FHIR framework** ([arXiv:2506.13800](https://arxiv.org/pdf/2506.13800)) wrap the same HL7 FHIR standard that MedAgentBench and FHIR-AgentBench use as *evaluation* environments, but for production deployment rather than benchmarking. Vendor platforms now ship this as a managed product: Anthropic's Claude for Healthcare bundles FHIR-development and prior-authorization Agent Skills with connectors to the CMS Coverage Database, ICD-10, and the NPI Registry, while Claude for Life Sciences connects to Medidata, ClinicalTrials.gov, bioRxiv/medRxiv, Open Targets, and ChEMBL ([Anthropic](https://www.anthropic.com/news/healthcare-life-sciences)) — with OpenAI reported to have shipped an analogous bundle around the same period, though that was not independently verified in this pass.

A third layer is the **biomedical MCP-server ecosystem** proper: **BioMCP** alone exposes 24 tools unifying PubTator3, Europe PMC, ClinVar, UniProt, MyGene.info, and MyDisease.info behind one MCP interface installable directly into Claude Code or Desktop, and a dedicated **BioContext.ai registry** now exists purely to index the growing number of such servers — evidence that "expose a biomedical database as an MCP tool" has become its own small sub-industry rather than a one-off research contribution. A fourth layer — **structured data commons that tools query rather than tools themselves** — underlies much of the above: Harvard's **Therapeutics Data Commons (TDC/TDC-2)** (66+ datasets, 22 tasks, an explicitly "API-first" multimodal retrieval layer designed for agentic workflows) and **PrimeKG** (17,080 diseases, 4.05M relationships, integrated directly into TDC-2) come from the same lab as ToolUniverse and TxAgent, suggesting one research group has built a vertically integrated stack from raw structured data through tool-wrapping through application-level reasoning. Finally, a narrower **tool-calling-specific benchmark layer** has emerged distinct from the clinical-reasoning benchmarks already covered: **BioTool** (7,040 verified query→API-call pairs over 34 NCBI/Ensembl/UniProt tools) is the clearest biomedical analog to BFCL/ToolBench, scoped to genomics/proteomics calls rather than clinical FHIR actions, and its headline finding — a fine-tuned 4B model outperforming GPT-5.1 on biomedical tool-calling — parallels the general-domain report's ReWOO distillation result (175B→7B) as a second, independent data point for "specialist fine-tuning beats generalist prompting" on tool-calling specifically.

Two structural observations cut across all five layers and point toward open angles for a workshop paper. First, the ecosystem is **not benchmarked against itself**: no source located in this pass runs a clinical-reasoning benchmark (MedAgentBench, FHIR-AgentBench) with a general tool catalog (ToolUniverse, Biomni) as the backend rather than the benchmark's own narrow built-in toolset, so it is unknown whether giving an agent a 1,000-tool catalog helps, hurts (via the general-domain report's documented tool-count-vs-accuracy collapse, e.g. BFCL's 43%→2% drop from 4 to 51 tools), or is neutral on a clinical safety-oriented task. Second, the "awesome list" layer tracking this space is itself fragmented — at least seven independently maintained, overlapping curated lists were found (`Awesome-AI-Agents-for-Healthcare`, `Awesome-Medical-LLMs-and-Agents`, `Awesome-AI4Med`, `awesome-medical-imaging-agents`, and others) — which is consistent with, and further evidence for, the companion report's framing of this field as "genuinely dense and still-fragmenting." For a paper positioning novelty against this landscape, the cleanest open contribution is the first point: nobody has measured whether general-purpose biomedical tool catalogs (ToolUniverse-class) help or hurt on the clinical safety-outcome metrics the companion report already identifies as underexplored (under-triage rate, not aggregate accuracy) when substituted into an existing clinical-reasoning benchmark's tool-calling slot.
